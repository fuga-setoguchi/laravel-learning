# SCR-05 学習記録（SQL）

作成日: 2026-11-27
ステータス: 確定（2026-11-27）
対応要件: FR-15

## 1. 概要

| 項目 | 内容 |
| --- | --- |
| パス | `GET /records`（`records`）。実行する SQL は `?sql=` で受け取る |
| Controller | `RecordsController`（`__invoke`） |
| ビュー | `resources/views/records.blade.php` |
| 目的 | 学習記録（回答履歴・復習の状態・レッスンの完了など）を、自分で SQL を書いて確かめる。自分のデータを題材に SQL を練習する |

集計の画面（グラフなど）は作らない。見たい切り口は、利用者が SQL で作る。よく使う切り口は「サンプルのクエリ」（5章）として用意する。

## 2. 方針

- **SELECT しかできない専用のユーザーで実行する**（4章）。アプリがふだん使う `app` ユーザー（Docker の PostgreSQL ではスーパーユーザー）では、利用者の SQL を実行しない
- 文字列で「SELECT で始まるか」を調べる方法には頼らない。守りは、DB の権限と、読み取り専用のトランザクションで行う
- SQL の実行は状態を変えない操作なので、**GET のフォーム**で送る（[方式設計書](../02_architecture.md) 3.3「状態を変えない送信は GET フォーム」。事前の問いと同じ扱い）。実行した結果の URL を再読み込み・ブックマークできる
- JavaScript は使わない

## 3. レイアウト

左のメニューは共通レイアウト（[LAYOUT](LAYOUT_common.md)）。以下は本文の部分。

テーブルと列は、SQL を書くときに必ず見るものなので、入力欄の**すぐ横に常に表示**する（開閉の操作をしなくても見える）。

```
│                                   │    result varchar        │
│ ③ 結果  12 行（12 ms）               │      remembered | vague …│
│ ┌────────────┬───────┐            │    answered_on date      │

│ └────────────┴───────┘            │    …                     │
```

- この画面だけ、本文の最大幅を広げる（ほかの画面は 60rem のまま）
- 結果の表が横に長いときは、表の部分だけ横にスクロールする

### 3.2 幅が狭い画面（1024px 未満）

2列にすると入力欄が狭くなりすぎるため、テーブルと列を**入力欄の上**に置く。`<details open>`（最初から開いた状態）にし、慣れたら閉じて入力欄を上に寄せられるようにする。

```
┌─────────────────────────────────┐
│ 学習記録（SQL）                   │
│ ▼ テーブルと列（開いた状態）         │
│   review_logs  id, question_id… │

│ └─────────────────────────────┘ │
```

HTML では、テーブルと列は1か所だけに書き、CSS（グリッドの配置）で幅ごとの位置を変える。

## 4. 項目定義

| No | 項目 | 内容 |
| --- | --- | --- |
| 1 | SQL の入力欄 | `<textarea name="sql">`。実行した SQL をそのまま入れ直して表示する。`maxlength` は 4000（6.1） |
| 2 | 実行する | GET フォームで `records` へ送信（`?sql=...`） |
| 3 | 結果 | 成功: 行数・実行時間・表（列名と値）。失敗: エラーの文言（6.4）。`sql` がないか空のときは表示しない |
| 4 | サンプルのクエリ | `<details>` の中に、見出しと SQL を並べる。見出しは `records?sql=（SQL）` へのリンクで、押すとその SQL を実行した画面になる |
| 5 | テーブルと列 | テーブルごとに、列名・型・参照先・取りうる値を並べる（位置は3章、表示は4.1、取得は6.5） |

### 4.1 テーブルと列の表示

今のテーブルは8つ・列は合わせて59（`migrations` を除く）。すべてを1画面に収めると文字が小さくなりすぎるため、1列を1行で小さめの文字で表示し、右の列の中だけスクロールできるようにする。よく見る学習記録のテーブル（`review_logs`・`review_states`・`lesson_progress`、合わせて21列）を先頭に置き、スクロールせずに見えるようにする。

| 表示するもの | 内容 | 例 |
| --- | --- | --- |
| テーブル名 | 太字の見出し。押すと、そのテーブルの列をたためる（4.1.1） | `review_logs` |
| 列名と型 | 1列1行。型は薄い色・小さい文字で、列名の後ろに並べる。型は短い名前にする（`character varying` → `varchar`、`timestamp without time zone` → `timestamp`） | `answered_on date` |
| 参照先 | 外部キーの列は、次の行に `→ questions.id` | JOIN を書くときの手がかり |
| 取りうる値 | 列挙値の列は、次の行に値を ` \| ` 区切りで並べる | `scheduled \| practice` |

- 文字は本文より小さくする（`0.8rem` 程度）
- テーブルの並びは、学習記録（`review_logs`、`review_states`、`lesson_progress`）を先に、教材（`chapters`、`lessons`、`questions`、`question_choices`、`lesson_sources`）を後にする。SQL で見ることが多いのは学習記録のため
- 列名は、選んでコピーしやすいよう、ただの文字として表示する（リンクにしない）

#### 4.1.1 たたむ

JavaScript を使わず、`<details>` / `<summary>` でたたむ。

| 単位 | たたむもの | 最初の状態 |
| --- | --- | --- |
| テーブルごと | テーブルの列の一覧。見出し（`<summary>`）はテーブル名と列の数（例: `review_logs（11）`） | 学習記録のテーブル（`review_logs`・`review_states`・`lesson_progress`）は開く。教材のテーブルはたたむ |

- 列ごとにはたたまない。補足（参照先・取りうる値）は1列につき1行だけで、たたんでも縦はほとんど縮まない。また、補足は JOIN や WHERE を書くときに見たいものなので、隠れていると開き直す手間が増える
- 開いた・たたんだ状態は覚えない。SQL を実行すると画面を読み込み直すため、最初の状態に戻る（覚えるには JavaScript か、状態を URL に含める仕組みが要るため、今回は入れない）。よく見るテーブルを最初から開いておくことで、戻っても困らないようにする

### 4.2 結果の表

- 列は、SQL の結果の列の順に、列名をそのまま見出しにする（同じ名前の列が2つあっても、両方表示する）
- 値の表示

| 値 | 表示 |
| --- | --- |
| NULL | `NULL`（薄い色で、文字列の "NULL" と見分けられるようにする） |
| 真偽値 | `true` / `false` |
| それ以外 | 文字列にしてそのまま（`{{ }}` でエスケープする） |

- 行が上限（500行）を超えたときは、500行だけ表示し、「500 行を超えたため、最初の 500 行だけ表示しています。」と表示する
- 結果が0行のときも、列名は表示し、「0 行」とする

## 5. サンプルのクエリ

`App\Records\SampleQueries::all()` に、見出しと SQL の組として持つ。

| 見出し | 内容 |
| --- | --- |
| 日ごとの回答数と正答率（直近14日） | `review_logs` を `answered_on` で集計。正解（`correct`・`remembered`）の割合 |
| 問題の種類ごとの正答率 | `review_logs` と `questions` を結合し、`type` ごとに集計 |
| よく間違える問題（上位10問） | 不正解（`incorrect`・`forgot`）の回数が多い問題と、そのレッスン |
| 段階ごとの問題数 | `review_states` を `stage` で集計 |
| 今後7日間の復習予定 | `review_states` を `next_review_on` で集計 |
| 章ごとのレッスンの完了数 | `chapters`・`lessons`・`lesson_progress` を結合して集計 |

- サンプルの SQL は、今のテーブルの定義で実行できることをテストで確かめる（テーブルを変えたときに、壊れたことに気づくため）

## 6. SQL の実行（App\Records\ReadOnlyQueryRunner）

### 6.1 受け付ける SQL

| 条件 | 扱い |
| --- | --- |
| `sql` がない・空白だけ | 実行しない（結果を表示しない） |
| 4000文字を超える | 実行せず、「SQL が長すぎます（4000 文字まで）。」 |
| 末尾の `;` と空白 | 取り除いてから実行する |
| 複数の文（`SELECT 1; DELETE ...`） | 受け付けない。PostgreSQL のプリペアドステートメントは1つの文しか受け付けないため、DB がエラーにする（6.3） |
| SELECT 以外の文（`DELETE`・`EXPLAIN`・`SHOW`・`SET`・`COMMIT`・`DO` など） | 6.2 の包み方で構文エラーになる。実行できるのは、`SELECT`・`WITH ... SELECT`・`VALUES` など、副問い合わせに書ける文だけ |

### 6.2 実行の手順

読み取り専用のユーザー用の接続（`pgsql_reader`、4章）で、次の順に実行する。

1. トランザクションを始める
2. `SET TRANSACTION READ ONLY`（読み取り専用のトランザクション）
3. `SET LOCAL statement_timeout = 5000`（5秒で中止）
4. **接続先を確かめる**（6.3 の守り 0）。`SELECT current_database(), rolsuper FROM pg_roles WHERE rolname = current_user` で、次のどちらかに当てはまれば、利用者の SQL を流さずに止める
   - スーパーユーザーである（`pgsql_reader` の設定を誤って `app` でつないだ）
   - 接続先の DB が、`pgsql` の接続先（`DB_DATABASE`）と違う
5. 利用者の SQL を次の形に包み、プリペアドステートメントで実行する。前後の改行は、利用者の SQL の末尾が `--` のコメントのとき、後ろの `)` と `LIMIT` がコメントに飲み込まれないようにするため

```sql
SELECT * FROM (
（利用者の SQL。末尾の ; と空白は取り除く）
) AS user_query LIMIT 501
```

6. 列名を取り出し、行を読む（501 行目があれば「上限を超えた」とし、表示は 500 行まで）
7. **成功しても失敗しても、必ずロールバックする**
8. 接続を切る（`DB::disconnect('pgsql_reader')`）。利用者の SQL が接続に残した設定を、次の実行に持ち越さないため

列名を取るため、Laravel の `select()`（列名をキーにした配列を返し、同じ名前の列が1つになる。0行のとき列名が分からない）ではなく、接続の PDO を直接使う。

上限の値（時間 5000 ミリ秒・行数 500・文字数 4000）は `config/learning.php` の `records` に持つ（テストで時間の上限を短くするため）。

### 6.3 守りの重ね方

| 守り | 内容 | 防げること |
| --- | --- | --- |
| 0. 実行前の接続先の確認 | 6.2 の 4 | 設定の誤りで、スーパーユーザーや別の DB で利用者の SQL を実行すること |
| 1. 読み取り専用のユーザー | `learning_reader`（4章）。テーブルへの権限は SELECT だけ。スーパーユーザーではない | 書き込み・削除・テーブルの変更。サーバー上のファイルの読み書きやコマンドの実行（`COPY ... TO PROGRAM`、`pg_read_file()` など。スーパーユーザーか特別な権限が必要） |
| 2. 読み取り専用のトランザクション | 6.2 の 2。アプリが毎回明示する（ユーザーの既定の `default_transaction_read_only = on` は、接続した本人が `SET` で変えられるため、それだけには頼らない） | 1 の権限の設定を誤ったときの書き込み |
| 3. 必ずロールバック・接続を切る | 6.2 の 7・8 | 万一書き込めた場合も、確定させない。接続に残る設定やロックを持ち越さない |
| 4. 1回に1文・SELECT として包む | プリペアドステートメント（6.1）と、6.2 の 5 の包み方。`DB::unprepared()` は使わない。`PDO::ATTR_EMULATE_PREPARES` を有効にしない（Laravel の既定は無効） | `COMMIT; DELETE ...` のように、トランザクションを抜けてから書き込む書き方。SELECT 以外の文 |
| 5. 時間の上限 | 5秒（6.2 の 3。ユーザーの既定でも 5秒） | 重いクエリで DB が固まること |
| 6. 行数の上限 | 6.2 の 5 の `LIMIT 501`（DB 側で絞る） | 大量の行で PHP のメモリが尽きること、画面が重くなること |

1 が本命で、0 は 1 の設定の誤りを実行前に捕まえるもの、2〜6 は保険と使いやすさのためのものとする。包み方（4）で SELECT 以外の文は構文エラーになるが、利用者の入力を SQL に埋め込む以上、それ単体を守りとは考えない。権限（1）が正しいことは、包み方を通さずに直接確かめるテスト（[SCR-05_test](../tests/SCR-05_test.md) T22）で保証する。

### 6.4 エラーの表示

PostgreSQL のエラーの文言（`SQLSTATE` とメッセージ）を、そのまま表示する（SQL の学習に役立つため）。ただし `QueryException` の文言は接続先などを含むため使わず、PDO のエラー情報（`errorInfo`）のメッセージだけを表示する。よくあるエラーには、日本語の説明を添える。

| SQLSTATE | 場面 | 添える説明 |
| --- | --- | --- |
| `25006` / `42501` | 書き込み・権限のない操作 | 「読み取り専用のため、データの変更はできません。」 |
| `57014` | 時間の上限 | 「5 秒以内に終わらなかったため、中止しました。」 |
| `42601` | 構文の誤り（複数の文・SELECT 以外の文を含む） | 「SELECT などの読み取りの文を、1つだけ書いてください。」 |

- 接続先の確認（6.2 の 4）で止めたときは、「読み取り専用の接続の設定が正しくないため、実行しませんでした。」と表示する（設定の値は表示しない）
- エラーの行番号は、包み方の1行目（`SELECT * FROM (`）の分だけ、入力より1つ大きくなる。行番号を使うエラーでは、「行番号は、入力した SQL の行より 1 つ大きくなります。」を添える

### 6.5 テーブルと列の一覧（App\Records\SchemaReader）

- 読み取り専用のユーザーの接続で、`public` スキーマの次の情報を読む。一覧の取得も 6.2 と同じ読み取り専用のトランザクションで行う
  - 列名と型: `information_schema.columns`（列の定義順）
  - 参照先: `information_schema` の外部キーの制約（`table_constraints`・`key_column_usage`・`constraint_column_usage`）
- `migrations` テーブルは表示しない（学習記録ではないため）
- テーブルの並び順は 4.1 のとおり、`SchemaReader` に持つ。並び順にないテーブル（今後足したもの）は、最後に名前順で並べる
- 取りうる値は、DB からではなく PHP の Enum から取る（DB の CHECK 制約は Enum の `values()` から作っており、同じ値になるため。[DB設計書](../03_database.md) 1章）

| 列 | Enum |
| --- | --- |
| `questions.type` | `QuestionType` |
| `review_logs.mode` | `ReviewMode` |
| `review_logs.result` | `ReviewResult` |
| `lesson_sources.kind` | `SourceKind` |

## 7. 制限

- 利用者の SQL の中の `?` と `:名前` は、PDO がプレースホルダーとして扱うことがある（文字列の中を除く）。jsonb の `?` 演算子は `??` と書く。画面の注意書きには書かない（使う場面がほとんどないため）
- `EXPLAIN`・`SHOW` などの SELECT 以外の文は使えない（6.1）
- GET で実行できるため、ほかのサイトのリンクや画像から実行させることはできる。ただし読み取り専用で時間の上限があり、実害はほぼない。POST と CSRF トークンにしても、DNS リバインディング（外部のサイトのドメインを 127.0.0.1 に向け直す手口）ではトークンごと読まれるため防げない。画面の内容をほかのサイトから読まれることは、受け付けるホスト名の確認（[方式設計書](../02_architecture.md) 6章）で防ぐ。再読み込み・ブックマーク・サンプルのクエリのリンクを使えるよう、GET のままとする
