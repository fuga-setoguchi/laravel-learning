## 概念

例外が起きたとき、Laravel は2つのことを別々に行います。

| 処理 | 何をするか | 誰のためか |
| --- | --- | --- |
| **報告**（report） | 例外をログや外部のサービスに記録する | 開発者・運用者 |
| **表示**（render） | 例外をレスポンス（エラーページや JSON）に変える | 利用者 |

公式ドキュメントによると、例外の扱いは `bootstrap/app.php` の `withExceptions` で設定します。報告は `$exceptions->report(...)`、表示は `$exceptions->render(...)` に書き、クロージャの引数の型で、どの例外に使うかが決まります。

```php
->withExceptions(function (Exceptions $exceptions): void {
    $exceptions->report(function (PaymentFailedException $e) {
        // 外部のサービスにも知らせる
    });

    $exceptions->render(function (PaymentFailedException $e, Request $request) {
        return response()->view('errors.payment-failed', status: 502);
    });
})
```

`report` に処理を足しても、ふだんのログへの記録は続けて行われます。止めたいときは `->stop()` を付けるか、`false` を返します。

## なぜ必要か

2つを分けて考えないと、「利用者に詳しいエラーを見せてしまう」「利用者には丁寧な画面を出したが、どこにも記録されていない」といった問題が起きます。運用者が知りたいこと（どの注文で、何が起きたか）と、利用者が知りたいこと（次に何をすればよいか）は違います。

公式ドキュメントによると、404 の HTTP エラーになる例外、オリジンの不一致による 403、CSRF のトークンが無効なことによる 419（第11章）などは、Laravel がもともと報告しません。報告させたいときは `stopIgnoring` で戻せます。直すべき問題ではないものまで記録すると、本当に調べるべき例外が埋もれます。自作の例外を報告させたくないときは、`$exceptions->dontReport([...])` に書くか、例外のクラスに `ShouldntReport` インターフェイスを実装します。

## どこに書くか

| やりたいこと | 書く場所 |
| --- | --- |
| 例外ごとの報告・表示を変える | `bootstrap/app.php` の `withExceptions` |
| 例外のクラスに報告・表示をまとめる | 例外のクラスの `report`・`render` メソッド |
| すべての例外のログに共通の情報を付ける | `bootstrap/app.php` の `$exceptions->context(fn () => [...])` |
| その例外のログに調査用の情報を付ける | 例外のクラスの `context` メソッド |
| 報告させない | `dontReport`、または `ShouldntReport` を実装 |

公式ドキュメントによると、ログインしているユーザーの id は、Laravel が自動で例外のログに付けます。すべての例外に共通の情報を足すなら `bootstrap/app.php` で `$exceptions->context(...)` を、その例外だけに足すなら例外のクラスに `context` を書きます。

```php
class PaymentFailedException extends Exception
{
    public function __construct(public readonly int $orderId) { parent::__construct('決済に失敗しました'); }

    public function context(): array
    {
        return ['order_id' => $this->orderId];
    }
}
```

## 良い例と悪い例

悪い例: 表示の処理の中で、ログも書く。

```php
$exceptions->render(function (PaymentFailedException $e) {
    Log::error('決済に失敗しました', ['message' => $e->getMessage()]);
    return response()->view('errors.payment-failed', status: 502);
});
```

なぜ悪いか: 例外はもともと報告されるので、ログが二重になります。記録している場所も散らばります。

公式ドキュメントによると、`$exceptions->dontReportDuplicates()` を呼ぶと、同じ例外のインスタンスは1回しか報告されません。ただし、これは例外の報告が重なるのを防ぐ設定です。`render` の中の `Log::error` は例外の報告ではないので、この設定では防げません。

良い例: 表示は `render`、調査用の情報は例外の `context` に書く。

## AIが書きがちな誤り

- `render` の中で `Log::error` を書き、報告と表示を混ぜる
- コントローラーごとに try / catch で、ログとエラー画面の処理をくり返す
- 利用者に、例外のメッセージをそのまま見せる
- 予想どおりに起きる例外まで報告し、ログを埋めてしまう

例外の処理を見たら、「これは記録のためか、利用者に見せるためか」を分けて考えましょう。

## まとめ

- 例外の扱いは、報告（記録）と表示（レスポンス）に分かれる
- `bootstrap/app.php` の `withExceptions` か、例外のクラスの `report`・`render` に書く
- 調査用の情報は `context` で足す。ユーザーの id は自動で付く
- 404 などは、もともと報告されない
