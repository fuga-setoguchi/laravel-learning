## 概念

公式ドキュメントによると、`config/app.php` の `debug` は、`APP_DEBUG` の値を使って、例外が起きたときにエラーの情報を利用者にどこまで見せるかを決めます。

```php
// config/app.php
'debug' => (bool) env('APP_DEBUG', false),
```

| 環境 | `APP_DEBUG` | 例外が起きたとき |
| --- | --- | --- |
| 開発 | `true` | 例外の詳細を画面に表示する |
| 本番 | `false` | 一般的なエラーページを表示する |

公式ドキュメントは、本番では `APP_DEBUG` を**必ず `false`** にするよう書いています。`true` のままだと、アプリの機密の設定値を利用者に見せてしまうおそれがあります。`.env` で環境ごとに値を変える仕組みは、第2章で扱いました。

## なぜ必要か

開発中の詳しいエラーの画面は、原因を探すのに便利です。どのファイルの何行目で起きたか、どんな値だったかがわかります。しかし本番で同じものが表示されると、それは攻撃者にとっての手がかりにもなります。ファイルの場所、使っているライブラリ、データベースの情報などから、次に狙う場所を探せます（一般的な考え方）。

一方、詳細を見せないからといって、記録まで消してはいけません。利用者には「次に何をすればよいか」だけを見せ、原因を調べるための詳しい情報は、開発者が見るログに残します。見せる相手が違うので、内容も分けます。

`APP_DEBUG` は、公開する前に本番の `.env` で確かめます。本番で設定をキャッシュしている場合は、`.env` を直しただけでは反映されず、キャッシュを作り直す必要があります（設定のキャッシュは第2章で扱いました）。「直したつもりで、詳細が出たまま」にならないよう、直した後にエラーの画面を確かめます（一般的な考え方）。

## どこに書くか

| 内容 | 置き場所 |
| --- | --- |
| 本番かどうかの切り替え | `.env` の `APP_DEBUG`（本番は `false`） |
| 利用者に見せる内容 | エラーページ（前のレッスンで扱いました）や、短いメッセージの JSON |
| 原因を調べる内容 | ログ（Laravel が報告した例外、`report($e)`） |

注意が必要なのは、自分でレスポンスを作るコードです。`APP_DEBUG` が決めるのは Laravel が作るエラーの画面やレスポンスなので、`$e->getMessage()` や `$e->getTraceAsString()` を自分で JSON に入れて返せば、本番でもそのまま利用者に届きます。

公式ドキュメントによると、`report($e)` を使うと、エラーページを表示せずに例外を報告できます。例外を受け止めて利用者向けのレスポンスを返すときは、`report($e)` で記録を残します。

## 良い例と悪い例

悪い例: 例外の中身を、そのまま利用者に返す。

```php
} catch (Throwable $e) {
    return response()->json(['error' => $e->getMessage()], 500);
}
```

なぜ悪いか: SQL の文や外部のサービスの情報が、`APP_DEBUG` と関係なく利用者に届きます。

良い例: 詳細はログに残し、利用者には短いメッセージを返す。

```php
} catch (PaymentFailedException $e) {
    report($e);

    return response()->json(['message' => '決済に失敗しました。時間をおいてやり直してください。'], 502);
}
```

## AIが書きがちな誤り

- 本番の `.env` で `APP_DEBUG=true` のままにする
- `$e->getMessage()` やスタックトレースを、レスポンスに入れて返す
- 詳細を見せないために、例外を受け止めて記録も残さない
- 「本番のサーバーなら詳細は出ない」と考える

エラーのレスポンスを見たら、「これは利用者に見せてよい内容か」「原因を調べる記録は残るか」を確かめましょう。開発中は詳細が見えるので、本番と同じ見え方になるかは、`APP_DEBUG` を `false` にして一度確かめておくと安心です。

## まとめ

- `APP_DEBUG` は、エラーの情報を利用者にどこまで見せるかを決める
- 本番では必ず `false` にする。`true` だと機密の設定値が見えるおそれがある
- 利用者には次にすべきことだけを見せ、詳しい情報はログに残す
- 例外の中身を自分でレスポンスに入れると、`APP_DEBUG` と関係なく漏れる
