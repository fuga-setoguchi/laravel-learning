## 概念

ログは、アプリで何が起きたかを後から調べるための記録です。公式ドキュメントによると、Laravel のログには、高い順に次の8つのレベルがあります。

| レベル | 使いどころの例（一般的な考え方） |
| --- | --- |
| `emergency`・`alert`・`critical` | システムが使えない、すぐに対応が必要 |
| `error` | 対応が必要な失敗（決済サービスにつながらない） |
| `warning`・`notice` | すぐには困らないが、注意したいこと |
| `info` | 記録しておきたいふつうの出来事（注文を受けた） |
| `debug` | 開発中の調べもの |

```php
Log::info('注文を受けました', ['order_id' => $order->id]);
Log::error('決済サービスに接続できません', ['order_id' => $order->id]);
```

公式ドキュメントによると、チャンネルの設定の `level` は、そのチャンネルに記録されるために必要な最低のレベルです。`level` が `warning` なら、`info` や `debug` は記録されません。

## なぜ必要か

レベルを正しく選ばないと、ログは役に立ちません。ふつうに起きる入力の誤りを `error` で記録すると、本当に対応が必要な失敗が埋もれます。逆に、障害を `debug` で記録すると、本番の設定では残らず、気づけません。

もう1つ大切なのは、ログに**残してはいけない**ものです。ログは、開発者や運用者、ログを集める外部のサービスなど、多くの人や仕組みが見ます。パスワード、トークン、カードの番号、必要以上の個人情報を書くと、ログから漏えいします。`$request->all()` をそのまま渡すと、送られてきたパスワードまで書かれます（一般的な考え方）。

どの利用者・どの注文で起きたかを後で追えるよう、ログには id を残します。名前やメールアドレスのような個人情報を書かなくても、id があればデータベースで調べられることが多いです（一般的な考え方）。

## どこに書くか

| やりたいこと | 書き方 |
| --- | --- |
| 調べるための情報を付ける | 2つ目の引数の配列（`['order_id' => $order->id]`） |
| そのリクエストのログすべてに情報を付ける | `Log::withContext([...])` や `Context::add(...)` |
| ログに出さずに持ち回る情報 | `Context::addHidden(...)` |
| Laravel が報告する例外のレベルを決める | `bootstrap/app.php` で `$exceptions->level(PDOException::class, LogLevel::CRITICAL)` |
| 機密情報を避ける | `$request->all()` を渡さず、必要な項目だけを選ぶ |

公式ドキュメントによると、`Log::withContext` を使うと、その後のログに同じ情報（リクエストの id など）を付けられます。`Context::add` で入れた情報も、ログに自動で付きます。`Context::addHidden` で入れた情報はログには付かず、`Context::get` では取り出せません。取り出すときは `Context::getHidden` を使います。

公式ドキュメントによると、Laravel が報告する例外も、`$exceptions->level(...)` で種類ごとに記録するレベルを決められます。「対応が必要な失敗は error 以上、ふつうの出来事は info 以下」という考え方は、`Log` を自分で呼ぶときだけでなく、例外の報告にも当てはまります。

メッセージに値を埋め込まず、配列で渡すと、メッセージは同じ文のまま情報が項目として残るので、検索や集計がしやすくなります（一般的な考え方）。

## 良い例と悪い例

悪い例: 送られてきた値をそのまま残す。

```php
Log::info('ログインに失敗しました', $request->all());
```

なぜ悪いか: 入力したパスワードが、そのままログに残ります。

良い例: 必要な項目だけを選んで残す。

```php
Log::info('ログインに失敗しました', [
    'email' => $request->input('email'),
    'ip' => $request->ip(),
]);
```

## AIが書きがちな誤り

- `$request->all()` やモデルの全項目を、そのままログに渡す
- ふつうに起きる入力の誤りを `error` で記録する
- 対応が必要な失敗を `debug` や `info` で記録し、本番で残らない
- 値をメッセージの文字列に埋め込み、検索しにくくする

ログを書くコードを見たら、「このレベルで本番に残るか」「機密情報が入っていないか」を確かめましょう。ログは書いた本人より、障害の調査で後から読む人のためのものです。

## まとめ

- ログのレベルは8つ。チャンネルの `level` より低いものは記録されない
- 対応が必要な失敗は `error`、ふつうの出来事は `info` 以下にする
- 調べるための情報は、2つ目の引数の配列や Context で付ける
- パスワードやトークンなどの機密情報は、ログに残さない
