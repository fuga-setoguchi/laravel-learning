## 概念

**ミドルウェア**は、リクエストがコントローラーに届く前や、レスポンスが返る前に処理をはさむ仕組みです。公式ドキュメントは、アプリに入ってくる HTTP リクエストを調べたり、ふるい分けたりする仕組みだと説明しています。例として、ログインしていない利用者をログイン画面にリダイレクトする認証や、すべてのリクエストを記録するログが挙げられています。

ミドルウェアは `handle` メソッドを持つクラスです。`$next($request)` を呼ぶと、リクエストは次のミドルウェアやコントローラーへ進みます。

```php
public function handle(Request $request, Closure $next): Response
{
    // 前処理: ここで止めるなら、$next を呼ばずにレスポンスを返す

    $response = $next($request);

    // 後処理: レスポンスを変える

    return $response;
}
```

ミドルウェアは `php artisan make:middleware` で作り、ルートに `->middleware(...)` で付けます。引数を渡すこともできます。

```php
Route::put('/posts/{post}', [PostController::class, 'update'])
    ->middleware(EnsureUserHasRole::class.':editor');
```

## なぜ必要か

多くのルートに共通する確認をコントローラーごとに書くと、書き忘れたコントローラーが穴になります。ミドルウェアにしてルートに付ければ、付けたルートすべてに同じ処理が行われます。

ただし、ミドルウェアの処理は、コントローラーを読んでも見えません。特定の機能だけの業務のロジック（割引の計算、在庫の引き当てなど）をミドルウェアに置くと、処理の流れを追うのが難しくなります。ミドルウェアには、どのルートにも同じように当てはまる処理だけを置きます（一般的な考え方）。

## どこに書くか

ミドルウェアに置くかどうかの見分け方は、一般的な考え方です。

| 処理 | 置き場所 |
| --- | --- |
| ログイン済みかの確認、利用者の役割による入口の制限 | ミドルウェア |
| リクエストのログ、レスポンスのヘッダーの追加 | ミドルウェア |
| 注文の金額の計算、在庫の更新、メール送信 | コントローラーやそこから呼ぶクラス |

ミドルウェアもコントローラーと同じくサービスコンテナが作るので、公式ドキュメントのとおり、必要なクラスはコンストラクタで受け取れます。ログを書くクラスなどを中で `new` せず、注入で受け取ります。

すべてのリクエストに付けるグローバルミドルウェアは、第1章で扱いました。一部のルートだけに付けるなら、ルートやルートのグループに付けます（グループはこの章の後のレッスンで扱います）。

## 良い例と悪い例

悪い例: レスポンスに付けたいヘッダーを、`$next` の前にリクエストへ付ける。

```php
$request->headers->set('X-Frame-Options', 'DENY');

return $next($request);
```

なぜ悪いか: 変わるのはリクエストのヘッダーで、ブラウザに返るレスポンスには付きません。

良い例: レスポンスを受け取ってから付ける。

```php
$response = $next($request);
$response->headers->set('X-Frame-Options', 'DENY');

return $response;
```

## AIが書きがちな誤り

- 特定の画面だけの業務のロジックを、ミドルウェアに置く
- レスポンスへの処理を `$next($request)` の前に書く
- 止める条件のときに、レスポンスを返さずに処理を続けてしまう

ミドルウェアを見つけたら、「どのルートにも同じように当てはまる処理か」「前処理と後処理の位置は正しいか」を確かめましょう。

## まとめ

- ミドルウェアは、リクエストを調べて通すか止めるかを決めたり、レスポンスに後処理をしたりする仕組み
- `$next($request)` の前が前処理、後が後処理。止めるときは `$next` を呼ばずにレスポンスを返す
- 多くのルートに共通する処理を置く。業務のロジックは置かない（一般的な考え方）
- ミドルウェアもコンテナが作るので、必要なクラスはコンストラクタで受け取れる
