## 概念

**FormRequest** は、検証の規則を持つ専用のリクエストのクラスです。公式ドキュメントは、検証と認可の処理を中に持つ独自のリクエストのクラスだと説明しています。

```php
// php artisan make:request StorePostRequest で app/Http/Requests に作られる
class StorePostRequest extends FormRequest
{
    public function authorize(): bool
    {
        return true;
    }

    public function rules(): array
    {
        return [
            'title' => ['required', 'max:100'],
            'body' => ['required'],
        ];
    }
}
```

コントローラーのメソッドで、このクラスを型宣言して受け取ります。

```php
public function store(StorePostRequest $request)
{
    $post = $request->user()->posts()->create($request->validated());

    return to_route('posts.show', ['post' => $post]);
}
```

公式ドキュメントによると、FormRequest はコントローラーのメソッドが呼ばれる前に検証されます。失敗すると、画面のフォームからのリクエストなら、エラーを付けて前の画面に戻すレスポンスが自動で返ります。XHR リクエスト（JavaScript からの非同期の通信）なら、エラーを含む 422 のレスポンスが返ります。Accept ヘッダーで JSON を求めるリクエストも、同じく 422 のレスポンスになります（公式ドキュメントの記載ではなく、Laravel 本体の実装による動き）。

## なぜ必要か

検証をコントローラーに書くと、コントローラーが入力の確認で長くなります。FormRequest に移せば、コントローラーには「検証を通った入力が届く」ことが約束され、本来の処理だけを書けます。検証の規則も、1つのクラスにまとまります。

コントローラーで `$request->validate([...])` を呼ぶ書き方も公式ドキュメントにあります。規則が短く、そのアクションでしか使わないなら、これでも構いません。規則が長くなったり、コントローラーが太ってきたりしたら、FormRequest に移します（一般的な考え方）。

## どこに書くか

| 書くもの | 置き場所 |
| --- | --- |
| 検証の規則 | FormRequest の `rules()` |
| 検証を通った入力の取り出し | コントローラーで `$request->validated()` や `$request->safe()->only([...])` |
| 検証に通った後の処理 | コントローラー、またはそこから呼ぶクラス |

保存には、`$request->all()` ではなく `$request->validated()` を使います。`all()` は、規則にない項目も含めて、送られてきた入力をすべて返します。

規則にない項目を、入口で弾くこともできます。FormRequest に `#[FailOnUnknownFields]` 属性を付けると、規則に書いていない項目が送られたときに、検証の失敗として扱われます。すべての FormRequest に適用するなら、`AppServiceProvider` の `boot` で `FormRequest::failOnUnknownFields()` を呼びます。

```php
use Illuminate\Foundation\Http\Attributes\FailOnUnknownFields;

#[FailOnUnknownFields]
class StorePostRequest extends FormRequest { /* ... */ }
```

公式ドキュメントは同じ節で、それでもモデルの `$fillable` / `$guarded` を設定し、信頼できる、検証済みの入力だけを保存するよう書いています。この属性を付けても、保存には `validated()` を使います。

`make:request` で作ったクラスの `authorize` は、そのままでは `false` を返します（Laravel 本体のひな形による動き）。`false` のままだと、すべてのリクエストが 403 になります。認可をここで行わないなら、`true` を返すか、`authorize` を消します。認可そのものは第8章で、検証の規則の考え方も第8章で扱います。

## 良い例と悪い例

悪い例: FormRequest で検証したのに、`all()` で保存する。

```php
$post = $request->user()->posts()->create($request->all());
```

なぜ悪いか: 規則にない項目も保存に渡ります。検証を通した意味が薄れます。

良い例: 検証を通った項目だけを使う。

```php
$post = $request->user()->posts()->create($request->validated());
```

## AIが書きがちな誤り

- FormRequest で検証したのに、`$request->all()` や `$request->input()` で保存する
- FormRequest を使っているのに、コントローラーでも同じ確認を `if` で書く
- `make:request` で作った `authorize` が `false` のままで、403 になる

FormRequest を受け取るコントローラーを見たら、「保存しているのは validated() の値か」を確かめましょう。

## まとめ

- FormRequest は検証の規則を持つリクエストのクラスで、コントローラーのメソッドが呼ばれる前に検証される
- 失敗すると、前の画面へのリダイレクト（XHR リクエストなら 422）が自動で返る
- コントローラーには検証を通った入力だけが届く。保存には `validated()` を使う
- ひな形の `authorize` は `false` を返すので、使わないなら `true` にする
