## 概念

公式ドキュメントは、コントローラーを「関連するリクエストの処理を1つのクラスにまとめるもの」と説明しています。コントローラーの仕事の中心は、リクエストとレスポンスをつなぐことです。

| コントローラーに書く | コントローラーの外に出す |
| --- | --- |
| 入力を受け取る | 業務の決まり（金額・割引の計算など） |
| 処理を担当するクラスを呼ぶ | 複数の手順からなる処理（保存・在庫の更新・通知） |
| 結果をビュー・リダイレクト・JSON にして返す | 外部サービスの呼び出し |

公式ドキュメントに書かれているのは、コントローラーが関連するリクエストの処理をまとめる、というところまでです。上の表のように、どこまでをコントローラーに書き、何を外に出すかは、一般的な考え方です。

## なぜ必要か

処理の入口は、HTTP のリクエストだけではありません。Artisan コマンド、キューのジョブ、スケジュールで動く処理からも、同じ業務の処理を使いたくなります。処理がコントローラーの中にあると、ほかの入口からは呼べず、書き写すことになります。書き写した処理は、片方だけ直されてずれていきます。

テストの書きやすさも変わります。処理がコントローラーにあると、リクエストを送るテストでしか確かめられません。外のクラスにあれば、そのクラスを直接呼んで、割引の計算のような細かい決まりを確かめられます。

## どこに書くか

コントローラーから出した処理の置き場所は、内容によって変わります。この章と、ほかの章で扱います。

| 処理 | 置き場所 |
| --- | --- |
| 入力の検証 | FormRequest（この章の次のレッスン） |
| 1つのユースケースの処理 | Action や Service のクラス（この章で扱う） |
| JSON の形を決める | API リソース（この章で扱う） |
| よく使う検索条件 | モデルのクエリスコープ（第6章） |
| 多くのルートに共通の前処理 | ミドルウェア（第4章） |

見分けるときは、「Artisan コマンドから同じことをするときにも必要な処理か」を考えます。必要なら HTTP に関係しない処理なので、外に出します。リダイレクトやフラッシュメッセージのように、コマンドでは不要な処理はコントローラーに残します（一般的な考え方）。

## 良い例と悪い例

悪い例: 注文の処理をすべてコントローラーに書く。

```php
public function store(StoreOrderRequest $request)
{
    $total = /* 金額と割引の計算 */;
    $order = $request->user()->orders()->create(['total' => $total]);
    // 在庫の更新、メール送信 ...

    return to_route('orders.show', ['order' => $order]);
}
```

なぜ悪いか: コマンドやジョブから同じ処理を使えず、テストもリクエストを送る形でしか書けません。

良い例: 処理を外のクラスに任せ、コントローラーはつなぐだけにする。

```php
public function store(StoreOrderRequest $request, PlaceOrder $placeOrder)
{
    $order = $placeOrder->handle($request->user(), $request->validated('items'));

    return to_route('orders.show', ['order' => $order])->with('status', '注文を受け付けました');
}
```

## AIが書きがちな誤り

- 計算・保存・通知まで、すべてを1つのアクションに書く
- 長くなったメソッドを、同じコントローラーの private メソッドに分けただけで済ませる
- 外に出したクラスの中で、リダイレクトやセッションなどの HTTP の処理まで行う

コントローラーのメソッドが10行を超えていたら、「HTTP に関係しない処理が混ざっていないか」を確かめましょう（行数は目安です）。

## まとめ

- コントローラーの仕事は、リクエストとレスポンスをつなぐこと
- 業務の決まり、複数の手順、外部サービスの呼び出しは、コントローラーの外に出す
- 外に出すと、コマンドやジョブからも使え、テストもしやすい
- 「コマンドからも必要な処理か」で見分ける（一般的な考え方）
