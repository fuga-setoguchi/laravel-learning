## 概念

**リソースコントローラー**は、1種類のデータ（リソース）に対する作成・表示・更新・削除を、決まった名前の7つのアクションで扱うコントローラーです。`Route::resource` の1行で、7つのルートがまとめて登録されます。

```php
Route::resource('photos', PhotoController::class);
```

| HTTP メソッド | URL | アクション | 役割 |
| --- | --- | --- | --- |
| GET | `/photos` | index | 一覧 |
| GET | `/photos/create` | create | 作成フォームの表示 |
| POST | `/photos` | store | 作成の処理 |
| GET | `/photos/{photo}` | show | 1件の表示 |
| GET | `/photos/{photo}/edit` | edit | 編集フォームの表示 |
| PUT/PATCH | `/photos/{photo}` | update | 更新の処理 |
| DELETE | `/photos/{photo}` | destroy | 削除 |

ルートの名前も `photos.index`・`photos.store` のように決まります。コントローラーは `php artisan make:controller PhotoController --resource` で、7つのメソッドのひな形付きで作れます。

一部だけ使うなら `->only([...])` や `->except([...])` で絞れます。API のように画面のいらない場合は、`create` と `edit` を除く `Route::apiResource` を使います。

## なぜ必要か

アクションの名前と URL が決まっていると、どのコントローラーを開いても、どこに何があるかを予測できます。AIが書いたコードを読むときも、「更新の処理なら update を見ればよい」とすぐにわかります。

規約に合わない操作が出てきたときに、`publish`・`archive`・`duplicate` のようなメソッドを同じコントローラーに足し続けると、この予測が効かなくなります。公式ドキュメントは、コントローラーの役割を絞っておくよう求め、7つのアクション以外のメソッドがたびたび必要になるなら、2つの小さなコントローラーに分けることを考えるよう勧めています。

## どこに書くか

規約に合わない操作をどう分けるかは、一般的な考え方です。

| 操作の例 | 分け方 |
| --- | --- |
| 記事を公開する・非公開にする | 「公開」をリソースとみなし、`PostPublicationController` の `store`・`destroy` にする |
| CSV を出力するなど、1つの操作だけ | 1アクションのコントローラー（`__invoke` だけを持つ） |

記事の「公開」のように、親のリソースに1つしかないものは、公式ドキュメントのシングルトンリソースとして登録できます。`creatable()` を付けると、作成と削除のルートも登録されます。

```php
// POST /posts/{post}/publication と DELETE /posts/{post}/publication
Route::singleton('posts.publication', PostPublicationController::class)
    ->creatable()
    ->only(['store', 'destroy']);
```

`creatable()` で増えるのは create・store・destroy で、表示や編集の show・edit・update も登録されます。`only` で必要なものだけに絞れます（`creatable()` と `only` を組み合わせられることは、公式ドキュメントの記載ではなく、Laravel 本体の実装で確認した動き）。

1アクションのコントローラーは `--invokable` を付けて作り、ルートではメソッド名を書かずに登録します。

```php
Route::post('/posts/{post}/publication', [PostPublicationController::class, 'store']);
Route::get('/exports/posts', ExportPostsController::class);
```

どうしても追加のルートを同じコントローラーに書くときは、公式ドキュメントのとおり、`Route::resource` より前に書きます。後に書くと、`/photos/{photo}` のようなリソースのルートが先に一致してしまいます。

## 良い例と悪い例

悪い例: 規約外のメソッドを同じコントローラーに足し続ける。

```php
Route::resource('posts', PostController::class);
Route::post('/posts/{post}/publish', [PostController::class, 'publish']);
Route::post('/posts/{post}/unpublish', [PostController::class, 'unpublish']);
```

なぜ悪いか: `PostController` が記事に関するあらゆる操作の置き場所になり、大きくなり続けます。

良い例: 操作を別のリソースとして切り出す。

```php
Route::resource('posts', PostController::class);
Route::post('/posts/{post}/publication', [PostPublicationController::class, 'store']);
Route::delete('/posts/{post}/publication', [PostPublicationController::class, 'destroy']);
```

## AIが書きがちな誤り

- 規約外のメソッド（`publish`、`approve` など）を、1つのコントローラーにいくつも足す
- 追加のルートを `Route::resource` の後に書き、リソースのルートに先に一致させてしまう
- API なのに `Route::resource` を使い、使わない `create`・`edit` のルートを残す

コントローラーのメソッド名を見たら、「7つのアクションのどれかに当てはまるか」を確かめましょう。当てはまらないものが増えていたら、分けどきです。

## まとめ

- リソースコントローラーは、index・create・store・show・edit・update・destroy の7つで1種類のデータを扱う
- create・edit はフォームの表示、store・update はその処理
- 規約に合わない操作は、別のリソースや1アクションのコントローラーに分ける
- 追加のルートは `Route::resource` より前に書く。API なら `Route::apiResource`
