## 概念

Laravel の認可には、2つの書き方があります。

**Gate** は、操作の名前とクロージャで認可を定義します。公式ドキュメントでは、`AppServiceProvider` の `boot` で定義しています。

```php
Gate::define('view-admin', fn (User $user) => $user->is_admin);
```

**Policy** は、特定のモデルについての認可を1つのクラスにまとめます。`php artisan make:policy PostPolicy --model=Post` で作り、操作ごとにメソッドを書きます。

```php
class PostPolicy
{
    public function update(User $user, Post $post): bool
    {
        return $user->id === $post->user_id;
    }

    public function create(User $user): bool
    {
        return $user->email_verified_at !== null;
    }
}
```

公式ドキュメントは、Gate と Policy をルートとコントローラーにたとえています。Gate はモデルに関係しない操作（管理画面を見るなど）に向き、特定のモデルに結び付く操作は Policy にまとめる、という使い分けです。

## なぜ必要か

モデルに結び付く認可を Gate に並べていくと、`AppServiceProvider` が `update-post`・`delete-post`・`update-comment`…と膨らみます。記事の認可を変えたいときに、どこを見ればよいかがわかりにくくなります。

Policy にまとめれば、「記事の認可は PostPolicy」と置き場所が決まります。メソッドの名前（`view`・`update`・`delete` など）がコントローラーのアクションと対応するので、どの操作の認可かも読み取りやすくなります。

## どこに書くか

| 認可 | 置き場所 |
| --- | --- |
| 記事の編集・削除など、モデルに結び付く操作 | Policy（`app/Policies/PostPolicy.php`） |
| 記事の作成など、対象のモデルがまだない操作 | Policy のユーザーだけを受け取るメソッド（`create(User $user)`） |
| 管理画面を見るなど、モデルに関係しない操作 | Gate（`AppServiceProvider` の `boot`） |

公式ドキュメントによると、Policy は規約に合えば自動で見つかります。モデルのディレクトリと同じ階層か上の `Policies` ディレクトリに置き、名前をモデル名＋`Policy`（`PostPolicy`）にします。規約に合わないときは、`Gate::policy` で登録します。

`--model` を付けて作った Policy には、`viewAny`・`view`・`create`・`update`・`delete` などのメソッドが用意されます。Laravel 本体のひな形では、どれも `false` を返すので、使う操作のメソッドを書き直します。

管理者に何でも許したいときは、Policy に `before` メソッドを書きます。公式ドキュメントによると、`before` が `null` 以外を返すと、その結果で判断が確定します。

```php
public function before(User $user, string $ability): bool|null
{
    if ($user->is_admin) {
        return true;
    }

    return null;   // ふだんどおり各メソッドで判断する
}
```

公式ドキュメントの警告によると、確かめる操作の名前と同じメソッドが Policy にないと、`before` は呼ばれません。`before` だけを書いて `publish` のメソッドを書いていなければ、`can('publish', $post)` は管理者でも拒否されます。

## 良い例と悪い例

悪い例: 記事の認可を Gate に並べる。

```php
Gate::define('update-post', fn (User $user, Post $post) => $user->id === $post->user_id);
Gate::define('delete-post', fn (User $user, Post $post) => $user->id === $post->user_id);
```

なぜ悪いか: モデルが増えるたびに `AppServiceProvider` が膨らみ、認可の置き場所が散らばります。

良い例: `PostPolicy` に `update` と `delete` を書く。

## AIが書きがちな誤り

- モデルに結び付く認可を、すべて Gate で定義する
- `before` で、管理者でないユーザーに `false` を返し、すべての操作を拒否する
- 「管理者には何でも許す」つもりで `before` だけを書き、確かめる操作のメソッドを Policy に書かず、管理者まで拒否される
- `make:policy --model` で作ったメソッドを、`false` のまま残す
- Policy を規約と違う場所や名前で作り、登録もせずに使われない

認可のコードを見たら、「モデルに結び付く操作なら Policy にあるか」を確かめましょう。

## まとめ

- モデルに結び付く認可は Policy、それ以外は Gate
- Policy は規約に合えば自動で見つかる（`app/Policies/PostPolicy`）
- 対象がまだない操作は、ユーザーだけを受け取るメソッドで書く
- `before` で判断を任せるときは `null` を返す
