## 概念

**検証**は、リクエストで届いた値が、アプリが受け付けてよい形かを確かめる処理です。第5章では、検証を FormRequest に置く理由を扱いました。このレッスンでは、どんな規則をどう組み立てるかを扱います。

Laravel には、たくさんの検証規則が用意されています。

```php
public function rules(): array
{
    return [
        'product_id' => ['required', 'integer', 'exists:products,id'],
        'quantity' => ['required', 'integer', 'between:1,10'],
        'status' => ['required', Rule::enum(OrderStatus::class)],
        'note' => ['nullable', 'string', 'max:500'],
    ];
}
```

1つの項目に、複数の規則を並べて組み立てます。

## なぜ必要か

画面側の検証（HTML の `required` や `max`、JavaScript）は、ブラウザで正しく操作したときにしか働きません。開発者ツールで書き換えたり、ブラウザを通さずにリクエストを送ったりすれば、どんな値でも届きます。画面側の検証は使いやすさのため、データを守るのはサーバー側の検証、と分けて考えます（一般的な考え方）。

検証が足りないと、マイナスの数量で在庫が増える、存在しないカテゴリの id が保存される、といった食い違ったデータが入ります。

## どこに書くか

1つの項目について、次の順に考えると、規則の漏れを防げます（一般的な考え方）。

| 確かめること | 規則の例 |
| --- | --- |
| 必須か、任意か | `required`、`nullable` |
| 型 | `integer`、`string`、`date`、`boolean` |
| 範囲・長さ | `between:1,10`、`min`、`max`（数の範囲なら `integer` や `numeric` と組み合わせる） |
| 決まった値の中にあるか | `in`、`Rule::enum(...)` |
| データベースの値との関係 | `exists`、`unique` |

`required` は「空でないこと」しか確かめません。型や範囲は、別の規則で確かめます。

公式ドキュメントによると、`integer` は、PHP の `FILTER_VALIDATE_INT` で整数として受け付けられる値を通し、変数の型が整数であることまでは確かめません。`'5'` のような文字列も通ります。型まで確かめたいときは `integer:strict` を使えます。数値であることを確かめるなら、`numeric` と組み合わせるよう勧めています。

`between`・`min`・`max` が数の大きさで比べるのは、`integer` や `numeric` と組み合わせたときです。公式ドキュメントの size の節によると、数値の規則がないと、値は文字列の長さとして比べられます。`['required', 'between:1,10']` だけだと、`'99999'` は5文字なので通ってしまいます。

任意の項目には `nullable` を付けます。公式ドキュメントによると、Laravel は既定で `TrimStrings` と `ConvertEmptyStringsToNull` のミドルウェアをグローバルミドルウェアに含めています。前後の空白が取り除かれ、空の文字列は `null` に変わるので、`nullable` がないと `date` などの規則で失敗します。

**データベースの値に依存する規則**には、注意点があります。`exists` は、id が実在するかを確かめます。持ち主の条件まで確かめたいときは、`Rule::exists` に条件を足します。

```php
'category_id' => [
    'required',
    Rule::exists('categories', 'id')->where('user_id', $this->user()->id),
],
```

`unique` で更新するときは、`ignore` で自分の行を除きます。公式ドキュメントは、`ignore` に利用者が操作できるリクエストの値を渡してはいけないとしています。認証済みのユーザーの id など、システムが決めた値を渡します。

## 良い例と悪い例

悪い例: 必須かどうかだけを確かめる。

```php
'quantity' => ['required'],
'category_id' => ['required'],
```

なぜ悪いか: `-5` や `'abc'`、存在しない id も通ります。

良い例: 型・範囲・存在まで確かめる。

```php
'quantity' => ['required', 'integer', 'between:1,10'],
'category_id' => ['required', 'exists:categories,id'],
```

## AIが書きがちな誤り

- `required` だけを並べて、型や範囲を確かめない
- `between` などを `integer` や `numeric` なしで使い、数ではなく文字列の長さで比べてしまう
- 画面側で選択肢を出しているからと、サーバー側の規則を省く
- 別のテーブルの id を受け取るのに、`exists` を付けない
- `unique` の `ignore` に、リクエストの値（隠し項目の id など）を渡す
- 任意の項目に `nullable` を付けず、空のときに検証で失敗する

検証規則を見たら、項目ごとに「型・範囲・存在は確かめているか」を確かめましょう。

## まとめ

- 画面側で検証していても、サーバー側で必ず検証する
- 必須か任意か、型、範囲、決まった値、データベースとの関係を順に考える
- 別のテーブルの id には `exists`、任意の項目には `nullable`
- `unique` の `ignore` には、システムが決めた値を渡す
