## 概念

データベースを使うテストでは、2つの道具を組み合わせます。

**データベースの初期化**: テストごとに、データベースを同じ状態に戻します。公式ドキュメントによると、`RefreshDatabase` トレイトは、スキーマが最新ならマイグレーションをやり直さず、テストをトランザクションの中で実行して、終わったら取り消します。Pest では、テストのファイルで `pest()->use(RefreshDatabase::class);` のように使います。

このアプリでは、`tests/Pest.php` で、`tests/Feature` のテストにまとめて `RefreshDatabase` を使う設定にしています。`tests/Unit` のテストはアプリを起動しない（この章の最初のレッスンで扱いました）ので、`RefreshDatabase` は付けていません。

**モデルのファクトリ**: テストデータを作る仕組みです。列の既定の値を `definition` にまとめておき、テストでは必要な値だけを上書きします。

```php
class PostFactory extends Factory
{
    public function definition(): array
    {
        return [
            'user_id' => User::factory(),
            'title' => fake()->sentence(),
            'status' => 'draft',
        ];
    }

    public function published(): static
    {
        return $this->state(fn (array $attributes) => ['status' => 'published']);
    }
}

$post = Post::factory()->published()->create(['title' => '公開記事']);
```

## なぜ必要か

前のテストのデータが残ると、テストの結果が、実行する順番や一緒に実行するテストによって変わります。単独では通るのに、まとめて実行すると落ちるテストは、原因を探しにくくなります。公式ドキュメントによると、`RefreshDatabase` はテストをトランザクションの中で実行するだけなので、このトレイトを使わないテストが追加したデータは、データベースに残ることがあります。一部のテストだけ使い忘れても、ほかのテストに影響が出ます。テストごとに初期化すれば、どのテストも同じ状態から始められます。

テストデータを `Post::create([...])` で、すべての列を書いて作ると、列が増えるたびに多くのテストを直すことになります。どの値がそのテストにとって大事なのかも読み取りにくくなります。ファクトリなら、既定の値はファクトリに任せ、テストには関係する値だけを書けます（利点の説明は一般的な考え方）。

## どこに書くか

| やりたいこと | 書き方 |
| --- | --- |
| テストごとにデータベースを初期化する | `RefreshDatabase` トレイト |
| 保存したデータを作る | `Post::factory()->create()` |
| 保存せずにモデルだけ作る | `Post::factory()->make()` |
| 何件か作る | `Post::factory()->count(3)->create()` |
| 決まった状態のデータを作る | `Post::factory()->published()->create()` |
| 関連するデータと一緒に作る | `User::factory()->has(Post::factory()->count(3))->create()` |
| 一部の値だけを変える | `Post::factory()->create(['title' => '...'])` |

テーブルを毎回作り直す `DatabaseMigrations` などもありますが、公式ドキュメントによると、`RefreshDatabase` よりずっと遅くなります。

`make()` は保存しないので、URL の id を使う HTTP テストには向きません。保存が必要なら `create()` を使います。

## 良い例と悪い例

悪い例: 前からあるデータや id に頼る。

```php
$post = Post::find(1);   // シーダーや前のテストで作られた記事に頼る
$this->get('/posts/1')->assertSee($post->title);
```

なぜ悪いか: データや id がいつも同じとは限らず、実行する順番や環境で結果が変わります。

良い例: そのテストに必要なデータを、テストの中でファクトリで作る。

```php
$post = Post::factory()->create(['title' => 'テストの記事']);
$this->get("/posts/{$post->id}")->assertSee('テストの記事');
```

## AIが書きがちな誤り

- テストごとにデータベースを初期化せず、前のテストのデータに結果が左右される
- `Post::find(1)` のように、決まった id や、シーダーのデータに頼る
- すべての列を書いて `Model::create` でテストデータを作る
- 保存が必要なのに `make()` を使い、404 になる

テストを見たら、「このテストは、単独でも、どの順番で実行しても同じ結果になるか」を確かめましょう。

## まとめ

- テストごとにデータベースを初期化し、どのテストも同じ状態から始める
- `RefreshDatabase` は、テストをトランザクションの中で実行して取り消す
- テストデータはファクトリで作り、テストには関係する値だけを書く
- `make()` は保存しない、`create()` は保存する
