## 概念

テストで確かめるのは、実装の内部ではなく、外から見える**振る舞い**です（一般的な考え方）。

| 確かめる（振る舞い） | 確かめない（実装の内部） |
| --- | --- |
| レスポンス（行き先、表示、ステータス） | どのクラスのどのメソッドが呼ばれたか |
| データベースの状態 | 中で使っている変数や手順の順番 |
| 送ったメール、入れたジョブ、外部へのリクエスト | private なメソッドの戻り値 |

ただし、メールの送信や外部 API の呼び出しを、テストのたびに本物で行うわけにはいきません。Laravel には、本物の代わりに記録だけを行う**フェイク**が用意されています。公式ドキュメントも、テストの中で実際には実行させたくない部分を差し替える方法として、イベントやジョブなどを差し替える仕組みを用意していると説明しています。

```php
Queue::fake();
Mail::fake();

$this->actingAs($user)->post('/orders', $data);

Queue::assertPushed(SendInvoice::class);
Mail::assertSent(OrderPlaced::class);
```

## なぜ必要か

内部の呼び出しを確かめるテストは、中の書き方に結び付きます。動きを変えずにクラスを分けたり名前を変えたりしただけで失敗し、逆に、モックが本物と違う動きをすると、本当は壊れていても通ります。テストが「直すたびに書き直すもの」になると、テストを信頼できなくなります。

一方、外への影響を止めないと、テストを実行するたびに本物のメールが送られたり、外部のサービスにデータが送られたりします。公式ドキュメントによると、`Queue::fake()` はジョブが実際にキューに入るのを止め、`Mail::fake()` はメールの送信を止めます。テストのときは `phpunit.xml` で `QUEUE_CONNECTION` が `sync` になっていることが多く（Laravel 本体のひな形による設定）、フェイクがないとジョブはテストの中でその場で実行されます。

## どこに書くか

| 外への影響 | フェイク | 確かめ方 |
| --- | --- | --- |
| キューのジョブ | `Queue::fake()` | `Queue::assertPushed(SendInvoice::class)` |
| メール | `Mail::fake()` | `Mail::assertSent(OrderPlaced::class)`、キューに入れるメールは `Mail::assertQueued(OrderPlaced::class)` |
| イベント | `Event::fake([OrderPlaced::class])` | `Event::assertDispatched(OrderPlaced::class)` |
| 外部の API（HTTP クライアント） | `Http::fake([...])` | `Http::assertSent(...)` |

公式ドキュメントによると、メールをキューに入れて送っている場合（メールのクラスに `ShouldQueue` を実装している場合など）は、`assertSent` ではなく `assertQueued` で確かめます。`assertSent` のままだと、メールを送る処理が正しくてもテストは失敗します。

公式ドキュメントによると、`Event::fake()` を呼ぶと、リスナーは一切実行されません。モデルのイベント（`creating` で UUID を付けるなど）に頼るファクトリを使うときは、ファクトリでデータを作った後に `Event::fake()` を呼ぶよう書かれています。すべてのイベントを止めるとこうした処理まで止まるので、`Event::fake([OrderPlaced::class])` のように対象のイベントを指定します（イベントとリスナーは第9章で扱いました）。

公式ドキュメントによると、`Http::preventStrayRequests()` を呼ぶと、偽の応答を決めていないリクエストは、本物に送られずに例外になります。偽物にし忘れた API の呼び出しに気づけます。

モックやフェイクにするのは、外への影響があるもの（メール、キュー、外部 API）に絞ります。データベースへの保存のように、テストの中で確かめられるものは本物を使います（一般的な考え方）。ジョブをフェイクにしたときは、ジョブの中身を別のテストで確かめます。たとえば、ジョブのインスタンスを作って `handle` を直接呼び、外部の API は `Http::fake()` で偽の応答にしたうえで、送った内容や保存された結果を確かめます（一般的な考え方）。

## 良い例と悪い例

悪い例: 内部のクラスをモックにして、呼ばれたことだけを確かめる。

```php
$this->mock(PlaceOrder::class, fn (MockInterface $mock) => $mock->expects('handle')->once());
$this->actingAs($user)->post('/orders', $data);
```

なぜ悪いか: 注文を保存する本物の処理が動かず、Action が壊れていても通ります。

良い例: 本物を動かして結果を確かめ、外への影響だけをフェイクにする。

```php
Queue::fake();

$this->actingAs($user)->post('/orders', $data);

$this->assertDatabaseHas('orders', ['user_id' => $user->id]);
Queue::assertPushed(SendInvoice::class);
```

## AIが書きがちな誤り

- 外への影響がない内部のクラスまでモックにし、「呼ばれた」ことだけを確かめる
- フェイクを使わず、テストのたびに本物のメールや外部 API を呼ぶ
- キューに入れるメールを、`assertQueued` ではなく `assertSent` で確かめる
- ジョブをフェイクにしたまま、ジョブの中身をどこでも確かめない
- private なメソッドを、無理に呼び出してテストする

テストを見たら、「中の書き方を変えても、動きが同じなら通るか」「外への影響を止めているか」を確かめましょう。

## まとめ

- 確かめるのは外から見える振る舞い（レスポンス、データベース、送ったもの）
- 外への影響（メール、キュー、外部 API）は、フェイクで止めて記録を確かめる
- 外への影響がないものは、モックにせず本物を動かす
- フェイクにしたジョブの中身は、別のテストで確かめる
