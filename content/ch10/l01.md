## 概念

Laravel のアプリには、テストのフォルダが2つあります。

| フォルダ | 種類 | 確かめるもの |
| --- | --- | --- |
| `tests/Feature` | 機能テスト | 複数のオブジェクトの組み合わせ、HTTP のリクエストからレスポンスまで |
| `tests/Unit` | 単体テスト | 小さく切り離したコード（1つのクラスやメソッド） |

公式ドキュメントによると、`tests/Unit` のテストは Laravel のアプリを起動しません。そのため、データベースやほかのフレームワークの機能は使えません。`php artisan make:test` で作るとテストは `tests/Feature` に、`--unit` を付けると `tests/Unit` に置かれます。

```php
// tests/Feature/PostTest.php（機能テスト）
it('記事を作成できる', function () {
    $this->actingAs(User::factory()->create())
        ->post('/posts', ['title' => '初めての投稿', 'body' => '本文'])
        ->assertRedirect();
});

// tests/Unit/DiscountTest.php（単体テスト）
it('ゴールド会員は1割引きになる', function () {
    expect((new DiscountCalculator)->apply(1000, Rank::Gold))->toBe(900);
});
```

テストは `php artisan test` で実行します。`--testsuite=Feature` のように、種類を絞って実行することもできます。公式ドキュメントによると、テストのときは `phpunit.xml` の設定で環境が `testing` になり、セッションやキャッシュは `array` のドライバーを使います。ただし、設定がキャッシュされていると `phpunit.xml` の値が使われず、開発用の設定（データベースなど）のままテストが実行されることがあります。公式ドキュメントも、テストを実行する前に `php artisan config:clear` で設定のキャッシュを消すよう書いています（設定のキャッシュは第2章で扱いました）。

## なぜ必要か

公式ドキュメントは、たいていのテストは機能テストにするのがよい、としています。機能テストは、ルート・ミドルウェア・検証・データベースまで通して確かめるので、「部品は正しいのに、つないだら動かない」という失敗を見つけられます。

一方、計算のように組み合わせが多いコードを、すべて機能テストで確かめると、1つずつリクエストを送ることになり、遅く、書くのも大変です。入力から結果が決まるコードは、単体テストで細かく試すほうが向いています（一般的な考え方）。

## どこに書くか

使い分けは、一般的な考え方です。

| 確かめたいこと | テスト |
| --- | --- |
| フォームの送信、画面の表示、認可、データベースへの保存 | 機能テスト |
| 計算・変換など、データベースやフレームワークに頼らないロジックの細かい組み合わせ | 単体テスト |
| 迷ったとき | 機能テスト |

単体テストにしたいなら、そのロジックをデータベースに頼らないクラスに切り出しておく必要があります。第5章で扱った Action のように、処理をクラスに分けておくと、テストもしやすくなります。

## 良い例と悪い例

悪い例: データベースを使うテストを `tests/Unit` に置く。

```php
// tests/Unit/OrderTest.php
it('注文を保存できる', function () {
    $order = Order::factory()->create();   // アプリが起動していないので失敗する
});
```

なぜ悪いか: `tests/Unit` ではアプリが起動しないので、データベースを使えません。

良い例: データベースを使うテストは `tests/Feature`、計算だけのテストは `tests/Unit` に置く。

## AIが書きがちな誤り

- データベースや HTTP のリクエストを使うテストを、`tests/Unit` に置く
- すべてを単体テストにしようとして、モックだらけのテストにする
- 計算の細かい組み合わせを、1つずつリクエストを送る機能テストで確かめる
- 「単体テストのほうが正しい」と考え、つないだときの動きを確かめない
- 開発環境で `config:cache` や `optimize` を実行したまま、テストを実行する

テストを見たら、「このテストはアプリの起動が必要か」「何を確かめたいのか」を確かめましょう。

## まとめ

- 機能テストは組み合わせやリクエスト全体、単体テストは小さく切り離したコードを確かめる
- `tests/Unit` ではアプリが起動しないので、データベースは使えない
- 公式ドキュメントは、たいていのテストを機能テストにするよう勧めている
- 単体テストは、入力から結果が決まるロジックの細かい組み合わせに使う
