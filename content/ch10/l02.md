## 概念

**HTTP テスト**は、アプリにリクエストを送り、レスポンスとデータベースの状態を確かめる機能テストです。ブラウザを使わず、テストの中から直接リクエストを送ります。

```php
it('記事を作成できる', function () {
    $user = User::factory()->create();

    $response = $this->actingAs($user)->post('/posts', [
        'title' => '初めての投稿',
        'body' => '本文です',
    ]);

    $response->assertRedirectToRoute('posts.index');

    $this->assertDatabaseHas('posts', [
        'title' => '初めての投稿',
        'user_id' => $user->id,
    ]);
});
```

`get`・`post`・`put`・`patch`・`delete` でリクエストを送り、`actingAs` でログインしたユーザーとして送れます。公式ドキュメントによると、テストを実行するときは CSRF のミドルウェアが自動で無効になります。

## なぜ必要か

HTTP テストは、ルート・ミドルウェア・検証・認可・データベースへの保存までを、1回のリクエストで通して確かめます。「コントローラーは正しいのに、ルートに auth ミドルウェアがない」といった、つなぎ目の誤りも見つけられます。

ただし、確かめ方が甘いと、テストは通るのに何も守れていない、ということが起きます。ステータスコードだけを確かめるテストは、検証で失敗して入力画面に戻った場合も、ログイン画面に飛ばされた場合も通ってしまいます。

## どこに書くか

よく使う確かめ方は次のとおりです。

| 確かめたいこと | 書き方 |
| --- | --- |
| 決まった画面へのリダイレクト | `assertRedirectToRoute('posts.index')` |
| 検証のエラー | `assertInvalid(['title'])`、通ったことは `assertValid()` |
| 認可で拒否された | `assertForbidden()`（403） |
| 画面に表示された文言 | `assertSee('初めての投稿')` |
| データベースの状態 | `assertDatabaseHas('posts', [...])` |

テストで確かめることの選び方は、一般的な考え方です。

- 成功する場合だけでなく、失敗する場合も書く（他人の記事は 403、誤った入力は検証のエラー）
- ステータスコードだけでなく、行き先とデータベースの状態まで確かめる
- `assertRedirect()` のように行き先を指定しない確かめ方は、別の理由のリダイレクトでも通る

公式ドキュメントは、1つのテストではアプリへのリクエストを1回にするのがよい、としています。複数のリクエストを送ると、思わぬ動きをすることがあるからです。前提のデータはファクトリで作ります（次のレッスンで扱います）。

## 良い例と悪い例

悪い例: ステータスコードだけを確かめる。

```php
$this->actingAs($user)->post('/posts', $data)->assertStatus(302);
```

なぜ悪いか: 検証で失敗して入力画面に戻っても 302 なので、保存されていなくても通ります。

良い例: 他人の記事は更新できないことも確かめる。

```php
it('作成者以外は記事を更新できない', function () {
    $post = Post::factory()->create();

    $this->actingAs(User::factory()->create())
        ->put("/posts/{$post->id}", ['title' => '書き換え', 'body' => '本文'])
        ->assertForbidden();

    expect($post->fresh()->title)->not->toBe('書き換え');
});
```

## AIが書きがちな誤り

- ステータスコードだけを確かめ、データベースの状態を確かめない
- `actingAs` を忘れ、ログイン画面へのリダイレクトで `assertRedirect()` が通る
- 成功する場合だけを書き、他人の記事が 403 になることを確かめない
- 1つのテストで作成・更新・削除のリクエストを続けて送る

テストを見たら、「処理を壊したら、このテストは失敗するか」を考えましょう。

## まとめ

- HTTP テストは、リクエストを送ってレスポンスとデータベースの状態を確かめる
- `actingAs` でログインしたユーザーとして送る。CSRF はテストでは自動で無効
- 行き先とデータベースの状態まで確かめ、失敗する場合も書く
- 1つのテストでは、リクエストを1回にする
