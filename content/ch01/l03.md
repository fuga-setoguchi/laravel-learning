## 概念

リクエストのライフサイクルとは、ブラウザからリクエストが届いてから、レスポンスを返すまでに Laravel の中で起きることの順番です。

1. **入口**: すべてのリクエストは `public/index.php` から始まる
2. **アプリケーションの作成**: `bootstrap/app.php` からアプリケーション（サービスコンテナ）を作る
3. **HTTPカーネル**: リクエストをカーネルに渡す。カーネルは、まず「ブートストラッパー」を実行し、エラー処理・ログ・実行環境の判定などを設定する。このとき、サービスプロバイダを読み込む
4. **グローバルミドルウェア**: すべてのリクエストに適用するミドルウェアを、ルーティングの前に通す（例: メンテナンス中のリクエストを止める `PreventRequestsDuringMaintenance`）
5. **ルーティング**: ルーターが、リクエストに合うルートを決め、そのルートやグループに付いたミドルウェアを実行してから、コントローラーに処理を渡す。セッションの開始や CSRF トークンの検証は、`routes/web.php` のルートに適用される web ミドルウェアグループに含まれ、この段階で実行される
6. **レスポンス**: コントローラーが返したレスポンスがルートのミドルウェアを逆向きに通って戻り、ブラウザに送られる

## なぜ必要か

ライフサイクルを知っていると、「この処理はどの段階に置くべきか」を判断できます。たとえば、すべてのページで必要な確認をコントローラーに書くと、書き忘れたページが穴になります。ミドルウェアにすれば、対象のルートすべてに一律で適用されます。

AIは、古い構成の Laravel の書き方で提案することがあります。[Laravel 11 のリリースノート](https://laravel.com/docs/11.x/releases)によると、Laravel 11 以降の新規アプリでは、以前の `app/Http/Kernel.php`（HTTPカーネルのクラス）や `config/app.php` の providers 配列に当たる設定が、`bootstrap/app.php` と `bootstrap/providers.php` にまとめられています。ただし、この構成は新規アプリ向けで、既存のアプリに変更は求められていません。古いバージョンからアップグレードしてきたアプリには、`app/Http/Kernel.php` が残っていることがあります。まずプロジェクトの実際の構成を確かめ、それに合っているかで提案を判断しましょう。

## どこに書くか

| やりたいこと | 置き場所 |
| --- | --- |
| すべてのリクエストに共通の処理（ルーティングの前） | グローバルミドルウェア。`bootstrap/app.php` の `withMiddleware` で追加する |
| 一部のルートだけの共通の処理（ルートが決まった後） | ミドルウェアを、そのルートやルートのグループに付ける |
| サービスコンテナへの登録 | サービスプロバイダの `register` |
| イベントリスナーなどの登録 | サービスプロバイダの `boot` |
| 自分で作ったサービスプロバイダの登録 | `bootstrap/providers.php`（Laravel 11 以降の新規アプリ） |

サービスプロバイダは2段階で動きます。まず、すべてのプロバイダの `register` が呼ばれ、それが全部終わってから、各プロバイダの `boot` が呼ばれます。`register` の時点では、他のプロバイダの登録がまだ済んでいない可能性があります。そのため公式ドキュメントは、`register` ではコンテナへの結合だけを行い、イベントリスナーやルートは登録しないよう求めています。

## 良い例と悪い例

悪い例: `register` でイベントリスナーを登録している。

```php
public function register(): void
{
    $this->app->singleton(PaymentGateway::class, StripeGateway::class);
    Event::listen(OrderShipped::class, SendShipmentNotification::class);
}
```

なぜ悪いか: `register` の時点では、イベントの仕組みを含む他のサービスが準備できているとは限りません。今たまたま動いていても、プロバイダの順番が変わると壊れる可能性があります。

良い例: 結合は `register`、リスナーの登録は `boot` に分ける。

```php
public function register(): void
{
    $this->app->singleton(PaymentGateway::class, StripeGateway::class);
}

public function boot(): void
{
    Event::listen(OrderShipped::class, SendShipmentNotification::class);
}
```

## AIが書きがちな誤り

- 新規アプリなのに、`app/Http/Kernel.php` にミドルウェアを登録するよう提案する（Laravel 11 以降の新規アプリでは `bootstrap/app.php`）
- 新規アプリなのに、`config/app.php` の providers 配列にサービスプロバイダを追加するよう提案する（Laravel 11 以降の新規アプリでは `bootstrap/providers.php`）
- `register` でイベントリスナーやルートを登録する
- すべてのページに必要な確認を、各コントローラーに書き写す

提案された場所が、対象バージョンの公式ドキュメントと、プロジェクトの実際の構成に合っているかを確かめましょう。

## まとめ

- 入口は public/index.php。bootstrap/app.php → カーネル → グローバルミドルウェア → ルーター → コントローラーの順に進む
- グローバルミドルウェアはルーティングの前、ルートやグループのミドルウェア（web グループのセッション・CSRF検証など）はルートが決まった後に実行される
- サービスプロバイダは register（結合だけ）→ boot（リスナーなどの登録）の2段階
- Laravel 11 以降の新規アプリの登録場所は bootstrap/app.php と bootstrap/providers.php。アップグレードしたアプリは古い構成のこともある
