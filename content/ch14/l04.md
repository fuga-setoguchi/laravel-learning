## 演習の進め方

最後の演習では、コントローラーからジョブまでつながった、月次のレポートを作る機能をレビューします。開発中は正しく動きます。

使う知識は、すべての章です。1つの観点だけでは見落とすので、次の順で何度か読み直しましょう（一般的な考え方）。

1. データを守れているか
2. 失敗したときにどうなるか
3. 量が増えたとき、本番の設定で動くか
4. 置き場所と書き方

## レビュー対象のコード

```php
// app/Models/Report.php
class Report extends Model
{
    protected $guarded = [];
}

// ReportController
public function store(Request $request)
{
    $request->validate(['month' => ['required', 'date_format:Y-m']]);

    DB::transaction(function () use ($request) {
        $report = Report::create($request->all());
        BuildMonthlyReport::dispatch($report);
    });

    return redirect('/reports');
}

// app/Jobs/BuildMonthlyReport.php の handle()
public function handle(): void
{
    try {
        $orders = Order::where('user_id', $this->report->user_id)
            ->whereBetween('created_at', $this->report->period())
            ->get();

        $total = 0;
        foreach ($orders as $order) {
            $total += $order->items->sum('price');
        }

        Http::withToken(env('PDF_API_TOKEN'))
            ->post('https://pdf.example.com/render', ['total' => $total])
            ->throw();
    } catch (Throwable $e) {
        Log::info('レポートの作成に失敗', ['user' => $this->report->user->toArray()]);
    }
}
```

## 見つけるべき問題

**1. 他人の注文のレポートを作れる（第11章・第5章）**

コントローラーは `user_id` を決めておらず、Report モデルは `$guarded = []` なので、フォームから送られた `user_id` がそのまま保存されます。書き換えて送れば他人のレポートを作れ、ジョブがその人の注文を集計するので、他人の売上が漏れます。代入してよい列を `month` だけにし、`$request->user()->reports()->create($request->validated())` にします。

**2. 例外を握りつぶしている（第12章・第9章）**

`catch` でログを書くだけなので、外部の API が落ちても、ジョブは成功したことになります。`catch` を外して Laravel に任せれば、失敗は failed_jobs に残ります。ただし、何も設定しないとジョブは1回しか試されないので、一時的な障害でやり直させるには `Tries` と `Backoff` で回数と間隔も決めます（第9章）。やり直しは `handle` の最初からなので、送信が2回行われても困らないか（冪等か）も確かめます。

**3. ログに個人情報を書いている（第12章）**

`toArray()` でメールアドレスなどの個人情報がすべてログに残り、レベルも `info` で、原因の例外も残りません。`catch` を外せば、例外は Laravel が報告します。

**4. 確定前にジョブを入れている（第9章）**

ワーカーが確定前に動くと、レポートが見つかりません。`afterCommit()` を付けます。

**5. 設定ファイルの外で env() を呼んでいる（第2章）**

本番で設定をキャッシュすると、トークンが読めなくなります。`config/services.php` に置き、`config()` で読みます。

**6. N+1 問題（第7章）**

注文ごとに明細を読み込むので、`with('items')` で先に読み込みます。

**7. 書き方と置き場所（第5章・第4章）**

検証は FormRequest に切り出し、リダイレクトは名前付きルートにします。

## 直したコード

```php
// ReportController
public function store(StoreReportRequest $request)
{
    DB::transaction(function () use ($request) {
        $report = $request->user()->reports()->create($request->validated());
        BuildMonthlyReport::dispatch($report)->afterCommit();
    });

    return to_route('reports.index');
}

// app/Models/Report.php
#[Fillable(['month'])]
class Report extends Model {}

// app/Jobs/BuildMonthlyReport.php
#[Tries(3)]
#[Backoff([10, 60])]
class BuildMonthlyReport implements ShouldQueue
{
    // use Queueable とコンストラクタは変更なし

    public function handle(): void
    {
        $orders = Order::where('user_id', $this->report->user_id)
            ->whereBetween('created_at', $this->report->period())
            ->with('items')
            ->get();

        $total = $orders->sum(fn (Order $order) => $order->items->sum('price'));

        Http::withToken(config('services.pdf.token'))
            ->post('https://pdf.example.com/render', ['total' => $total])
            ->throw();
    }
}
```

さらに見直すなら、次もあります。

- 合計だけなら、`withSum('items', 'price')` でデータベースに合計させる方法もあります（第13章の「集計はデータベースに任せる」）
- 決めた回数まで失敗したときに担当者へ知らせるなら、`failed` メソッドに書きます（第9章）

## まとめ

- データを守れているか。認可、検証済みの値、ログに残すものは適切か（第8・11・12章）
- 失敗したとき、食い違いが残らず、失敗が誰かに伝わるか（第7・9・12章）
- 本番の設定や、増えたデータでも動くか（第2・7・13章）
- 処理の置き場所と書き方は、Laravel の規約に沿っているか（第3・4・5章）
- 直したら、HTTP クライアントを偽物にしたテストで、同じ問題が戻らないようにする（第10章）
