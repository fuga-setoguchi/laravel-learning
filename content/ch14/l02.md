## 演習の進め方

このレッスンでは、AIが書いた「自分の支払い済みの注文の一覧」と「注文を受け付ける処理」をレビューします。開発中の少ないデータでは、どちらも正しく動きます。

使う知識は、次の章で扱ったものです。

| 章 | 主な観点 |
| --- | --- |
| 第6章 | マイグレーション、キャスト、スコープの使い方 |
| 第7章 | N+1 問題とトランザクション |
| 第13章 | インデックスと、取り出す量 |

データベース周りの問題は、データが少ないうちは見えません。「本番で行が数十万に増えたら」「書き込みの途中で失敗したら」と想像しながら読みましょう。

## レビュー対象のコード

```php
// database/migrations/..._create_orders_table.php（実行済み）
Schema::create('orders', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained();
    $table->string('status');
    $table->timestamps();
});

// OrderController
public function index(Request $request)
{
    $orders = Order::all()
        ->where('user_id', $request->user()->id)
        ->where('status', 'paid')
        ->sortByDesc('created_at');

    return view('orders.index', ['orders' => $orders]);
}

// resources/views/orders/index.blade.php の @foreach の中
{{ $order->created_at }}：{{ $order->items->count() }} 点

// app/Actions/PlaceOrder.php
public function handle(User $user, array $items): Order
{
    $order = $user->orders()->create(['status' => 'pending']);

    foreach ($items as $item) {
        $order->items()->create(['product_id' => $item['product_id'], 'qty' => $item['qty']]);
        Product::whereKey($item['product_id'])->decrement('stock', $item['qty']);
    }

    return $order;
}
```

## 見つけるべき問題

**1. 書き込みがトランザクションにまとまっていない（第7章）**

注文・明細・在庫の書き込みが並んでいるだけなので、途中で失敗すると、明細のない注文や、在庫だけが減った商品が残ります。`DB::transaction()` で包みます。データの食い違いは後から直すのが大変なので、最も重い問題です。

**2. 全件を取り出してから PHP で絞り込んでいる（第13章）**

`Order::all()` は、他人の分も含めたすべての注文をメモリに載せます。その後の `where`・`sortByDesc` は、コレクションの上での処理です。ログインしているユーザーのリレーションから取り出し、絞り込み・並べ替えをクエリで書き、`paginate` で1ページ分だけ取り出します。

**3. 一覧で N+1 問題が起きている（第7章）**

ビューの `$order->items->count()` は、注文ごとに明細を読み込みます。件数だけなので、`withCount('items')` で数えて、`$order->items_count` で表示します。

**4. 状態を文字列で扱っている（第6章）**

`'paid'`・`'pending'` を、使う場所ごとに文字列で書いています。列挙型のキャストにし、「支払い済み」の条件はローカルスコープにまとめます。

**5. 一覧の検索に合うインデックスがない（第13章・第6章）**

直した一覧は、`user_id` と `status` で絞り込み、`created_at` で並べ替えます。外部キーの列に自動でインデックスが作られるかは、データベースによって違います（MySQL の InnoDB は作り、PostgreSQL は作りません。データベースの一般的な知識）。複合インデックスは「絞り込む列 → 並べ替える列」の順に並べるので、`['user_id', 'status', 'created_at']` を足します（第13章）。実行済みのマイグレーションは書き換えず、新しいマイグレーションで足します（第6章）。

## 直したコード

```php
// 新しいマイグレーション
Schema::table('orders', function (Blueprint $table) {
    $table->index(['user_id', 'status', 'created_at']);
});

// Order モデル
protected function casts(): array
{
    return ['status' => OrderStatus::class];
}

#[Scope]
protected function paid(Builder $query): void
{
    $query->where('status', OrderStatus::Paid);
}

// OrderController@index
$orders = $request->user()->orders()
    ->paid()
    ->withCount('items')
    ->latest()
    ->paginate(20);

// ビュー
{{ $order->created_at }}：{{ $order->items_count }} 点

// PlaceOrder
return DB::transaction(function () use ($user, $items) {
    $order = $user->orders()->create(['status' => OrderStatus::Pending]);
    // 明細の作成と在庫の更新（変更なし）
    return $order;
});
```

一覧は、必要な行だけを1ページ分、明細の件数と一緒に取り出すようになりました。受け付けの処理は、すべて成功するか、すべて取り消されるかのどちらかになります。

## まとめ

データベース周りをレビューするときは、次を確かめます。

- 複数の書き込みが、途中で失敗しても食い違いを残さないか（第7章）
- `all()`・`get()` の後に、PHP で絞り込んでいないか。必要な分だけ取り出しているか（第13章）
- ループやビューの中で、リレーションを1件ずつ読み込んでいないか（第7章）
- 状態の値や検索の条件を、キャストやスコープにまとめているか（第6章）
- よく使う検索に合うインデックスがあるか。足すときは新しいマイグレーションで（第13章・第6章）
