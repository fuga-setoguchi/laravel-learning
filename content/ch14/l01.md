## 演習の進め方

このレッスンでは、AIが書いた「注文を更新する」コントローラーをレビューします。コードは動き、自分の注文を正しく更新できます。それでも、複数の問題があります。

使う知識は、次の章で扱ったものです。

| 章 | 主な観点 |
| --- | --- |
| 第3章 | 依存を中で作らず、注入で受け取っているか |
| 第4章 | ルートモデル結合と名前付きルートを使っているか |
| 第5章 | コントローラーが太っていないか、検証を切り出しているか |
| 第8章 | 検証の規則は十分か、認可を処理の前に確かめているか |

先に「見つけるべき問題」を読まずに、自分で問題を書き出してから読み進めましょう。重大なものから順に並べられると、なお良いです。

## レビュー対象のコード

```php
// routes/web.php
Route::put('/orders/{id}', [OrderController::class, 'update'])->middleware('auth');

// app/Http/Controllers/OrderController.php
class OrderController extends Controller
{
    public function update(Request $request, int $id)
    {
        $order = Order::find($id);

        $request->validate([
            'quantity' => ['required'],
            'note' => ['nullable', 'string', 'max:500'],
        ]);

        $order->update($request->all());

        $notifier = new OrderNotifier(config('services.slack.webhook'));
        $notifier->updated($order);

        return redirect('/orders/' . $order->id);
    }
}
```

## 見つけるべき問題

重大なものから順に並べます。

**1. 他人の注文を更新できる（第8章）**

`auth` ミドルウェアは、ログインしているかを確かめるだけです。URL の id を書き換えれば、他人の注文も更新できます。Policy に `update` を書き、ルートに `can('update', 'order')` を付けて、処理の前に確かめます。

**2. 検証の規則が足りない（第8章）**

`quantity` が `required` だけなので、`abc` や `-5` も通ります。`integer`・`min:1` のように、受け付けてよい値を規則で決めます。

**3. 検証していない項目まで保存に渡している（第5章）**

`$request->all()` には、規則に書いていない項目も含まれます。検証を通った値だけを `validated()` で渡します。検証の規則は FormRequest に切り出し、コントローラーを薄く保ちます。

**4. id で自分で探している（第4章）**

`Order::find()` は、見つからないと `null` を返し、次の `update()` でエラーになります。ルートを `{order}` にし、ルートモデル結合で受け取れば、見つからないときは 404 になります。

**5. 依存を中で組み立てている（第3章）**

`new OrderNotifier(...)` と書くと、テストで偽物に差し替えられず、テストのたびに本当の通知が飛びます。コンストラクタで受け取り、組み立てはサービスプロバイダに任せます。

**6. URL を文字列で組み立てている（第4章）**

`'/orders/' . $order->id` は、URL を変えたときに直し漏れが出ます。名前付きルートを使い、`to_route()` でリダイレクトします。

1 と 2 は、他人のデータが書き換わったり、ありえない値が保存されたりする問題です。3 から 6 は、すぐには壊れなくても、直し漏れやテストのしにくさにつながります。レビューでは、まずデータを守れているかを見て、次に書き方を見る、という順で確かめると、重大な問題を見落としにくくなります（一般的な考え方）。

## 直したコード

```php
// routes/web.php
Route::put('/orders/{order}', [OrderController::class, 'update'])
    ->middleware('auth')
    ->can('update', 'order')
    ->name('orders.update');

// UpdateOrderRequest の rules()
return [
    'quantity' => ['required', 'integer', 'min:1', 'max:99'],
    'note' => ['nullable', 'string', 'max:500'],
];

// OrderController
class OrderController extends Controller
{
    public function __construct(private OrderNotifier $notifier) {}

    public function update(UpdateOrderRequest $request, Order $order)
    {
        $order->update($request->validated());
        $this->notifier->updated($order);

        return to_route('orders.show', ['order' => $order]);
    }
}

// AppServiceProvider の register()
$this->app->bind(OrderNotifier::class, fn () => new OrderNotifier(config('services.slack.webhook')));
```

コントローラーに残ったのは、「検証済みの値で更新し、通知し、画面を返す」という流れだけです。認可はルート、検証は FormRequest、組み立てはサービスプロバイダと、それぞれの置き場所に移りました。

さらに見直すなら、Slack への通知もあります。外部のサービスへの通知は時間がかかり、失敗もしやすいので、キューに回す候補になります（第9章）。この演習の観点からは外れるので、ここでは直していません。

## まとめ

コントローラーをレビューするときは、次を確かめます。

- 他人のデータを扱えないよう、処理の前に認可を確かめているか（第8章）
- 検証の規則が、受け付けてよい値を決めているか。保存には `validated()` を渡しているか（第5章・第8章）
- モデルはルートモデル結合で受け取り、リダイレクトは名前付きルートを使っているか（第4章）
- 依存は注入で受け取っているか（第3章）
- 重大なもの（データを守れているか）から順に見ているか
