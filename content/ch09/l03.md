## 概念

**イベント**は、「何かが起きた」ことを表すクラスです。**リスナー**は、そのイベントが起きたときに実行される処理です。

```php
// app/Events/OrderPlaced.php
class OrderPlaced
{
    use Dispatchable, SerializesModels;

    public function __construct(public Order $order) {}
}

// 起点: 注文が確定したことを知らせる
OrderPlaced::dispatch($order);

// app/Listeners/SendOrderConfirmation.php
class SendOrderConfirmation implements ShouldQueue
{
    public function handle(OrderPlaced $event): void
    {
        Mail::to($event->order->user)->send(new OrderConfirmed($event->order));
    }
}
```

公式ドキュメントは、イベントを、アプリのいろいろな部分を切り離す方法として説明しています。注文が発送されたら Slack に通知する例で、注文の処理と通知の処理を結び付けず、イベントを発行する形を示しています。

`php artisan make:event` と `make:listener` で作ります。公式ドキュメントによると、`app/Listeners` に置いたリスナーは、`handle` の引数の型を見て、自動でイベントと結び付けられます。リスナーに `ShouldQueue` を実装すると、キューで実行されます。

## なぜ必要か

注文の確定の後に、確認メール、営業への通知、売上の集計…と処理が増えていくと、注文の処理がそれらをすべて知ることになります。イベントにすれば、注文の処理は「確定した」と知らせるだけで、後の処理はリスナーとして足したり外したりできます。

一方で、イベントには弱点もあります（ここからは一般的な考え方）。起点のコードを読んでも、何が実行されるかが見えません。リスナーがさらにイベントを発行すると、流れはもっと追いにくくなります。処理に欠かせない手順までリスナーに隠すと、「注文したのに在庫が減らない」ような不具合の原因を探しにくくなります。

## どこに書くか

どちらに書くかの見分け方は、一般的な考え方です。

| 手順 | 置き場所 |
| --- | --- |
| 処理に欠かせず、順番どおり必ず成功させたい（在庫を減らす、支払いを記録する） | 起点の Action などに直接書く |
| 起点と独立した後の処理（通知、集計、外部への連携） | イベントのリスナー |
| リスナーのうち時間がかかるもの | `ShouldQueue` を実装したリスナー |

キューで実行するリスナーは、イベントを発行したリクエストとは別に、ワーカーが後で実行します。リスナーが失敗しても、起点の処理は成功したまま進みます。欠かせない手順をリスナーに置かない、もう1つの理由です（一般的な考え方）。

登録されているイベントとリスナーは、`php artisan event:list` で一覧にできます。起点のコードから流れが見えないときは、この一覧で、どのリスナーが反応するかを確かめます。

## 良い例と悪い例

悪い例: 処理に欠かせない手順を、リスナーに任せる。

```php
OrderPlaced::dispatch($order);
// 在庫を減らすのは DecrementStock リスナー
```

なぜ悪いか: 注文の処理を読んでも在庫が減ることがわからず、注文の作成とまとめて扱えません。

良い例: 欠かせない手順は直接書き、後の処理だけをイベントにする。

```php
DB::transaction(function () use ($order) {
    // 注文の作成と在庫の更新
});

OrderPlaced::dispatch($order);   // 確認メール・通知はリスナー
```

## AIが書きがちな誤り

- 在庫の更新のような欠かせない手順まで、リスナーに置く
- 時間のかかるリスナーに `ShouldQueue` を付けず、リクエストを待たせる
- リスナーの中でイベントを発行し、処理を連鎖させる
- 1つのリスナーしかなく、増える見込みもないのに、イベントにする

イベントを見たら、「この手順が動かなかったら、処理そのものが壊れるか」を確かめましょう。

## まとめ

- イベントは、処理の起点と後の処理を切り離す
- 使いすぎると、何が実行されるかがコードから見えなくなる
- 欠かせない手順は直接書き、独立した後の処理をリスナーにする
- 時間のかかるリスナーは `ShouldQueue` でキューに入れる
