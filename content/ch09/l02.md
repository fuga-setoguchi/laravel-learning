## 概念

ジョブは、失敗すると、決めた回数まで**やり直し**ができます。公式ドキュメントによると、何も設定しないとジョブは1回しか試されません。回数とやり直しの間隔は、ジョブのクラスに属性で書けます。

```php
use Illuminate\Queue\Attributes\Backoff;
use Illuminate\Queue\Attributes\Tries;

#[Tries(3)]
#[Backoff([10, 60])]   // 1回目の失敗の後は10秒、それ以降は60秒待つ
class SendInvoice implements ShouldQueue
{
    use Queueable;

    public function handle(): void { /* ... */ }

    public function failed(?Throwable $exception): void
    {
        // 決めた回数まで失敗したときの後始末（管理者への通知など）
    }
}
```

決めた回数まで失敗すると、ジョブは `failed_jobs` テーブルに記録され、`failed` メソッドが呼ばれます。原因を直した後、`php artisan queue:retry` で実行し直せます。

やり直しでは、`handle` が最初から実行されます。そのため、ジョブは**冪等**（べきとう）に書きます。冪等とは、同じ処理が2回以上実行されても、結果が1回のときと変わらないことです（一般的な用語）。

## なぜ必要か

ジョブが途中まで進んでから失敗すると、やり直しで、成功した手順がもう一度実行されます。「ポイントを付ける」「メールを送る」のような手順が、試すたびにくり返されます。

やり直し以外にも、同じジョブが2回実行されることがあります。公式ドキュメントによると、ジョブのタイムアウトが接続の `retry_after` より長いと、終わる前に別のワーカーがもう一度実行することがあります。「ジョブは2回以上実行されることがある」と考えて書くのが安全です（一般的な考え方）。

## どこに書くか

冪等にする書き方は、一般的な考え方です。

| 手順 | 冪等にする書き方 |
| --- | --- |
| 数を足す（ポイントの付与など） | 付与したことを記録し、すでにあれば足さない |
| 状態を変える | 「支払い済みにする」のように、何回実行しても同じ状態になる書き方にする |
| 外部への送信 | 送信済みの記録を確かめる。外部サービスに重複を防ぐ仕組みがあれば使う |

公式ドキュメントによると、ジョブに `ShouldBeUnique` を実装すると、同じジョブがキューに同時に1つしか入らないようにできます（キャッシュのドライバーがロックに対応している必要があります）。ただし、これは「同じジョブを重ねて入れない」ための仕組みです。失敗したときのやり直しで `handle` が最初から実行されることは防がないので、冪等に書く必要はなくなりません（一般的な考え方）。

失敗したときの扱いも決めておきます。

- やり直したい失敗は、例外を投げて `handle` を終える
- 例外を受け止めてログに書くだけにすると、ジョブは成功したことになり、やり直しも `failed_jobs` への記録も起きない
- 決めた回数まで失敗したときの後始末は、`failed` メソッドに書く

## 良い例と悪い例

悪い例: やり直すたびに、ポイントが足される。

```php
public function handle(CrmClient $crm): void
{
    $this->user->increment('points', 500);
    $crm->notifyBonus($this->user->id, 500);   // ここで失敗すると、最初からやり直し
}
```

なぜ悪いか: 外部 API で失敗するたびに、ポイントが500ずつ増えます。

良い例: 付与したことを記録し、すでにあれば足さない。

```php
public function handle(CrmClient $crm): void
{
    $grant = BonusGrant::firstOrCreate(['user_id' => $this->user->id, 'type' => 'signup']);

    if ($grant->wasRecentlyCreated) {
        $this->user->increment('points', 500);
    }

    $crm->notifyBonus($this->user->id, 500);
}
```

この書き方は、`bonus_grants` テーブルの `user_id` と `type` の組み合わせに、一意制約を付けておくことが前提です。`firstOrCreate` は「探して、なければ作る」の2段階なので、同じジョブが同時に2つ実行されると、どちらも「なかった」と判断することがあります。重複を確実に防ぐのは、データベースの一意制約です（一般的な考え方）。`firstOrCreate` と `increment` を同時に失敗させないためには、第7章で扱ったトランザクションでまとめます。

## AIが書きがちな誤り

- 数を足す処理を、やり直しを考えずにジョブに書く
- `ShouldBeUnique` を付ければ、やり直しても安全（冪等）になると考える
- `handle` の中で例外を受け止めてログに書くだけにし、やり直しも記録もされない
- やり直しの回数を設定せず、一時的な失敗でもすぐに失敗扱いにする
- `failed` メソッドで後始末をせず、失敗したことに誰も気づかない

ジョブを見たら、「この `handle` が2回実行されたら、何が起きるか」を考えましょう。

## まとめ

- ジョブは、何も設定しないと1回しか試されない。回数と間隔は `Tries`・`Backoff` で決める
- やり直しは `handle` の最初から。2回実行されても困らない（冪等な）書き方にする
- 例外を受け止めて終わらせると、やり直しも `failed_jobs` への記録も起きない
- 決めた回数まで失敗したら、`failed` メソッドと `queue:retry` で扱う
