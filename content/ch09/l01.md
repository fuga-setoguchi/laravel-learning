## 概念

**キュー**は、時間のかかる処理を、リクエストとは別に後で実行する仕組みです。処理は**ジョブ**のクラスに書き、キューに入れます（ディスパッチ）。キューに入ったジョブは、**ワーカー**と呼ばれる別のプロセスが取り出して実行します。

```php
class SendWelcomeMail implements ShouldQueue
{
    use Queueable;

    public function __construct(public User $user) {}

    public function handle(): void
    {
        Mail::to($this->user)->send(new WelcomeMail($this->user));
    }
}

SendWelcomeMail::dispatch($user);   // キューに入れて、すぐ次へ進む
```

`php artisan make:job` で作ると、`ShouldQueue` を実装し、`Queueable` トレイトを使うクラスができます。公式ドキュメントによると、ジョブに Eloquent のモデルを渡すと、キューにはモデルの id だけが保存され、実行するときにデータベースから取り出し直されます。そのため、キューに入れてから実行されるまでにモデルが変わっていれば、変わった後の値で処理されます。公式ドキュメントによると、その間にモデルが削除されていると、ジョブは失敗します。ジョブのクラスに `#[DeleteWhenMissingModels]` 属性を付ければ、モデルが見つからないときは例外を出さずにジョブを捨てられます。どちらにするかは、そのジョブにとって、モデルが削除されたことが異常かどうかで決めます（一般的な考え方）。

読み込み済みのリレーションも一緒に保存され、実行時に取り出し直されます。公式ドキュメントによると、ジョブに不要なリレーションは `withoutRelations()` で外せます。

## なぜ必要か

公式ドキュメントは、アップロードされた CSV の取り込みのように、ふつうのリクエストの中では時間がかかりすぎる処理をキューに回すと、すぐにレスポンスを返せると説明しています。メールの送信、外部 API の呼び出し、画像や PDF の作成をリクエストの中で行うと、その間、利用者は画面が返るのを待つことになります。

外部のサービスは、遅くなったり一時的に失敗したりします。リクエストの中で失敗すると利用者にエラーが見えますが、ジョブなら、ワーカーが後でやり直せます（やり直しの設計は次のレッスンで扱います）。

## どこに書くか

キューに向くかどうかの見分け方は、一般的な考え方です。

| 処理 | キュー |
| --- | --- |
| メール送信、外部 API への送信、画像・PDF の作成 | 向く（時間がかかる、失敗しやすい、結果をすぐ使わない） |
| 入力の検証、作ったデータの id を使うリダイレクト | 向かない（結果をそのレスポンスで使う） |

ジョブのクラスは `app/Jobs` に置きます。キューに入れるだけでは実行されないので、ワーカーを動かします。

```bash
php artisan queue:work
```

公式ドキュメントによると、新しいアプリでは `database` の接続が既定のキューです。ワーカーは起動したときのアプリをメモリに持ち続けるので、コードを変えたら `php artisan queue:restart` で再起動します。公式ドキュメントによると、`queue:restart` は、今のジョブを終えたら終了するよう、ワーカーに指示するだけです。終了したワーカーを起動し直すには、Supervisor のようなプロセス管理の仕組みが必要です。仕組みがないまま実行すると、ワーカーは止まったままになり、ジョブが実行されなくなります。ワーカーのような長く動くプロセスでは、`singleton` に状態を持たせない注意も必要です（第3章で扱いました）。

`dispatchSync` を使うと、キューに入れずにその場で実行します。その場合は、レスポンスを待たせないという効果もなくなります。

## 良い例と悪い例

悪い例: 時間のかかる処理を、リクエストの中で行う。

```php
$order = $placeOrder->handle($user, $data);
$this->invoices->sendPdf($order);   // 数秒かかる
return to_route('orders.show', $order);
```

なぜ悪いか: 請求書の作成と送信が終わるまで、画面が返りません。

良い例: 結果をすぐ使わない処理は、ジョブにしてキューに入れる。

```php
$order = $placeOrder->handle($user, $data);
SendInvoice::dispatch($order);
return to_route('orders.show', $order);
```

## AIが書きがちな誤り

- メール送信や外部 API の呼び出しを、コントローラーの中でそのまま行う
- 結果をレスポンスで使う処理まで、ジョブに移す
- ジョブを作ったのに、ワーカーを動かす手順を書かない
- ジョブのコードを変えた後、ワーカーを再起動しない
- プロセス管理の仕組みがない環境で `queue:restart` を案内し、ワーカーを止めたままにする

リクエストの中の処理を見たら、「この結果を、今返す画面で使うか」を確かめましょう。

## まとめ

- 時間のかかる処理はジョブにして、ワーカーに後で実行させる
- 結果をそのレスポンスで使う処理は、キューに向かない
- ワーカー（`queue:work`）がないとジョブは実行されない。コードを変えたら再起動する
- ジョブに渡したモデルは、id だけが保存され、実行時に取り出し直される
