## 概念

**CSRF**（クロスサイトリクエストフォージェリ）は、ログインしている利用者のブラウザから、本人が意図しないリクエストを送らせる攻撃です。

公式ドキュメントの例では、悪意のあるサイトに、あなたのアプリの `/user/email` へ送るフォームを置き、ページを開いたときに自動で送信します。ブラウザはあなたのアプリのクッキーを付けて送るので、アプリからは本人のリクエストに見え、メールアドレスが攻撃者のものに変えられます。

Laravel は、セッションごとに**CSRF のトークン**を作ってセッションに保存し、リクエストに付いたトークンと一致するかを確かめます。悪意のあるサイトはトークンを知らないので、正しいリクエストを作れません。フォームには `@csrf` を書くと、トークンを入れた `_token` の隠し項目が出力されます。

```blade
{{-- POST で送るフォームの中に書く --}}
@csrf
```

## なぜ必要か

公式ドキュメントによると、確かめているのは `PreventRequestForgery` ミドルウェアで、`web` のミドルウェアグループに最初から含まれています（web グループは第1章で扱いました）。そのため、`routes/web.php` のルートは、何もしなくても守られています。

13.x のミドルウェアは、まずブラウザが送る `Sec-Fetch-Site` ヘッダーで、同じオリジンから送られたリクエストかを確かめます。確かめられなければ、これまでどおりトークンを確かめます。公式ドキュメントは、このヘッダーは HTTPS の接続でだけ送られると注意しています。サブドメインなど、同じサイトの別のオリジンからのリクエストも許したいときは、`preventRequestForgery(allowSameSite: true)` を指定します。

スキーム・ホスト・ポートがすべて同じなら同じオリジンで、サブドメインが違うと、同じサイトでも別のオリジンになります（一般的な知識）。

公式ドキュメントによると、トークンが一致しないときは、ふつう 419 のレスポンスになります。`originOnly: true` でトークンの確認をやめ、オリジンの確認だけにした場合は、確認に失敗すると 419 ではなく 403 になります。

守りが自動で効くぶん、問題になるのは「守りを外す」コードです。419 を消すために確認を外したり、データを変える処理を確認の対象外の GET にしたりすると、対策が効かなくなります。

## どこに書くか

| 場面 | 書き方 |
| --- | --- |
| Blade のフォーム | フォームの中に `@csrf` |
| JavaScript からのリクエスト | `X-CSRF-TOKEN` ヘッダーにトークンを付ける |
| 外部のサービスからの Webhook | `bootstrap/app.php` で `preventRequestForgery(except: [...])` |

公式ドキュメントによると、確認の対象は `POST`・`PUT`・`PATCH`・`DELETE`・`QUERY` のリクエストです。GET は確かめられないので、データを変える処理は GET のルートにしません（一般的な考え方）。

URI を外してよいのは、Stripe などの外部のサービスからの通知のように、送る側がトークンを付けられない場合です。テストでは CSRF のミドルウェアが自動で無効になる（第10章）ので、テストが通っても、フォームに `@csrf` があるとは限りません。

## 良い例と悪い例

悪い例: 419 を消すために、確認を外す。

```php
$middleware->preventRequestForgery(except: ['posts/*']);
```

なぜ悪いか: 記事の作成・更新・削除が、悪意のあるサイトから送らせたリクエストでも通ります。

良い例: フォームでトークンを送り、データを変える処理は GET にしない。

```php
Route::delete('/posts/{post}', [PostController::class, 'destroy'])
    ->can('delete', 'post');
```

```blade
{{-- 削除のフォームの中 --}}
@csrf
@method('DELETE')
```

公式ドキュメントによると、HTML のフォームは PUT・PATCH・DELETE のリクエストを送れないので、`_method` の隠し項目でメソッドを指定します。Blade では `@method('DELETE')` と書けば、この隠し項目が出力されます。

## AIが書きがちな誤り

- フォームが 419 になったとき、`@csrf` を足さずに、URI を確認から外す
- 削除やログアウトなど、データや状態を変える処理を GET のルートにする
- JavaScript からの POST に、トークンのヘッダーを付けない
- ログインや認可があれば CSRF は防げると考える

確認の除外や、データを変える GET のルートを見たら、「悪意のあるサイトから、本人のブラウザでこのリクエストを送らせたらどうなるか」を考えましょう。

## まとめ

- CSRF は、本人のブラウザから、本人のクッキー付きで意図しないリクエストを送らせる攻撃
- Laravel は web グループのミドルウェアで、トークン（13.x では先に Sec-Fetch-Site ヘッダーで同じオリジンか）を確かめる
- フォームには `@csrf`、データを変える処理は GET にしない
- 確認から外すのは、トークンを付けられない外部からの通知だけ
