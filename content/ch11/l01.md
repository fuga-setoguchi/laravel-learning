## 概念

**マスアサインメント**（一括代入）は、`create`・`update`・`fill` に配列を渡して、複数の列をまとめて代入することです。

```php
$post = Post::create(['title' => '初めての投稿', 'body' => '本文']);
```

便利ですが、リクエストの値をそのまま渡すと危険です。公式ドキュメントも、悪意のある利用者が `is_admin` のような項目をリクエストに足して送り、それが `create` に渡されると、自分を管理者にできてしまう例を挙げています。これが**マスアサインメントの脆弱性**です。

公式ドキュメントによると、Eloquent のモデルは、もともとマスアサインメントの脆弱性から守られています。一括で代入するには、モデルに `Fillable` 属性か `Guarded` 属性を付け、代入してよい列（または代入させない列）を決めます。

```php
use Illuminate\Database\Eloquent\Attributes\Fillable;

#[Fillable(['title', 'body'])]
class Post extends Model
{
}
```

13.x の公式ドキュメントは属性で書く方法を示していますが、モデルのプロパティ `protected $fillable = ['title', 'body'];` で書いても同じように働きます（Laravel 本体の実装による動き。このアプリのモデルもプロパティで書いています）。

## なぜ必要か

フォームに `is_admin` の入力欄がなくても、利用者はブラウザの開発者ツールや別のツールで、好きな項目を足して送れます。画面に出していない列でも、リクエストで書き換えを試みることはできます。

代入してよい列を決めておけば、それ以外の列は一括の代入では書き換わりません。公式ドキュメントによると、`Fillable` 属性に含まれない属性は、何も言わずに捨てられます。捨てられたことに気づかないと「保存したはずの値が入らない」という不具合になるので、開発中は `AppServiceProvider` の `boot` で `Model::preventSilentlyDiscardingAttributes(! $this->app->isProduction());` のように呼ぶと、本番以外では捨てる代わりに例外にできます（公式ドキュメントの例）。

## どこに書くか

| 守ること | 書く場所 |
| --- | --- |
| 一括で代入してよい列 | モデルの `Fillable` 属性（または `$fillable`） |
| そのフォームで受け取る項目 | FormRequest の規則と、コントローラーの `$request->validated()` |
| 作成者などシステムが決める値 | リレーションを通して作る（`$request->user()->posts()->create(...)`） |

代入してよい列はモデルごとの設定なので、フォームごとに受け取る項目を絞るには `validated()` を使います（`all()` との違いは第5章で扱いました）。作成者の `user_id` のように、利用者に決めさせてはいけない値は、代入してよい列に入れず、ログインしているユーザーから決めます（一般的な考え方）。

公式ドキュメントには、すべての列を代入できるようにする `Unguarded` 属性もありますが、その場合は `fill`・`create`・`update` に渡す配列を、毎回自分で組み立てるよう注意しています。

## 良い例と悪い例

悪い例: すべての列を許し、リクエストの値をそのまま渡す。

```php
protected $guarded = [];

Post::create($request->all());
```

なぜ悪いか: `user_id` や `is_pinned` を足して送れば、他人の名前で投稿したり、固定表示にしたりできます。

良い例: 代入してよい列を決め、検証済みの値をリレーションを通して渡す。

```php
#[Fillable(['title', 'body'])]
class Post extends Model {}

$request->user()->posts()->create($request->validated());
```

## AIが書きがちな誤り

- `MassAssignmentException` を消すために、`$guarded = []` ですべての列を許す
- `create($request->all())` や `update($request->all())` で、送られた項目をそのまま渡す
- `user_id` や `role` まで代入してよい列に入れ、リクエストの値で決める
- 代入してよい列を決めたことで安心し、`validated()` を使わない

モデルと `create` を見たら、「利用者が項目を足して送ったら、どの列まで書き換わるか」を確かめましょう。

## まとめ

- リクエストの値をそのまま一括で代入すると、フォームにない列まで書き換えられる
- モデルに代入してよい列を決める。それ以外は捨てられる
- フォームごとに受け取る項目は `validated()` で絞る
- 作成者などシステムが決める値は、リクエストではなくログインしているユーザーから決める
