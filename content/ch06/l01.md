## 概念

**マイグレーション**は、データベースのスキーマ（テーブルや列の定義）の変更を、PHP のコードとして書いたものです。公式ドキュメントは、データベースのバージョン管理のようなものだと説明しています。

```php
// php artisan make:migration create_posts_table で database/migrations に作られる
return new class extends Migration
{
    public function up(): void
    {
        Schema::create('posts', function (Blueprint $table) {
            $table->id();
            $table->string('title');
            $table->timestamps();
        });
    }

    public function down(): void
    {
        Schema::drop('posts');
    }
};
```

`up` には変更を、`down` には `up` を元に戻す処理を書きます。ファイル名の先頭の日時で、実行する順番が決まります。

`php artisan migrate` は、まだ実行していないマイグレーションだけを実行します。どれを実行済みかは、データベースの `migrations` テーブルに記録されます（公式ドキュメントでは、ロールバックの節に、`migrate:rollback` が戻す単位の「バッチ」の値を記録するテーブルとして出てきます）。`php artisan migrate:status` で、実行済みと未実行のものを確かめられます。

## なぜ必要か

公式ドキュメントは、マイグレーションが解決する問題として、変更を取り込んだ同僚に「ローカルのデータベースにこの列を手で足して」と伝える場面を挙げています。スキーマの変更をコードにしておけば、だれの環境でも、本番でも、`migrate` を実行するだけで同じスキーマになります。

ただし、この仕組みは「実行済みのものは実行しない」ことで成り立っています。実行済みのマイグレーションを書き換えても、ほかの環境ではもう一度実行されないので、変更が届きません。自分の環境だけ作り直して動いているように見えても、本番や同僚の環境とスキーマがずれます。変更は、新しいマイグレーションとして足します（一般的な考え方）。

## どこに書くか

| やりたいこと | 書き方 |
| --- | --- |
| テーブルを作る | 新しいマイグレーションで `Schema::create` |
| 既存のテーブルに列を足す・消す | 新しいマイグレーションで `Schema::table` |
| 既存の列の型や長さを変える | 新しいマイグレーションで `->change()`（残したい修飾子もすべて書く） |
| 開発中のデータベースを作り直す | `php artisan migrate:fresh`（すべてのテーブルを削除するので、開発用だけ） |

公式ドキュメントによると、`migrate:fresh` はテーブルの接頭辞に関係なく、すべてのテーブルを削除します。ほかのアプリと共有しているデータベースでは、そのアプリのテーブルも消えます。

データを失う可能性のある操作を本番で実行しようとすると、実行の前に確認を求められます。`--force` を付けると、この確認を飛ばせます。確認は、本番のデータを守るためのものです。

まだ自分の環境でしか実行していないマイグレーションなら、`migrate:rollback` で戻してから書き換えても、ほかの環境には影響しません。一度ほかの環境で実行されたら、書き換えないようにします（一般的な考え方）。

## 良い例と悪い例

悪い例: 実行済みの `create_posts_table` に列を書き足す。

なぜ悪いか: 本番や同僚の環境では実行済みなので、列が足されません。

良い例: 列を足す新しいマイグレーションを作る。

```php
// php artisan make:migration add_slug_to_posts_table
public function up(): void
{
    Schema::table('posts', function (Blueprint $table) {
        $table->string('slug')->nullable();
    });
}

public function down(): void
{
    Schema::table('posts', function (Blueprint $table) {
        $table->dropColumn('slug');
    });
}
```

## AIが書きがちな誤り

- 実行済みのマイグレーションを書き換えて、列を足す
- `->change()` で、元の `nullable()` や `default()` を書き忘れる
- 列の追加の手順として、`migrate:fresh` を案内する（データがすべて消える）。本番で確認を求められたときに、中身を確かめずに `--force` を付けて実行するよう案内する
- `down` を空のままにする

マイグレーションの変更を見たら、「このファイルは、もうほかの環境で実行されていないか」を確かめましょう。

## まとめ

- マイグレーションは、スキーマの変更をコードにして共有する仕組み
- `migrate` は未実行のものだけを実行し、実行済みかどうかは `migrations` テーブルに記録される
- 実行済みのマイグレーションは書き換えず、新しいマイグレーションで変更を足す
- `->change()` では残したい修飾子もすべて書く。`migrate:fresh` は開発用だけ
