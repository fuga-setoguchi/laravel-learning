## 概念

**インデックス**は、列の値から行の場所をすぐに引けるようにする、データベースの仕組みです。本の索引のようなもので、インデックスがない列で絞り込むと、データベースはテーブルのすべての行を順に読んで、条件に合うかを確かめます（データベースの一般的な動き）。

Laravel では、マイグレーションでインデックスを付けます。

```php
Schema::create('orders', function (Blueprint $table) {
    $table->id();
    $table->foreignId('user_id')->constrained();
    $table->string('status');
    $table->timestamps();

    $table->index('status');                     // 1つの列
    $table->index(['user_id', 'created_at']);    // 複合インデックス
});
```

公式ドキュメントによると、`unique` は値の重複を許さないインデックス、`index` はふつうのインデックスを作ります。複数の列をまとめた複合インデックスも作れます。

## なぜ必要か

行が少ないうちは、インデックスがなくても速く返るので、開発中には問題に気づきません。本番で行が数十万・数百万と増えると、すべての行を読む検索は、行が増えるほど遅くなります。同じ検索が多くの画面で使われていれば、データベース全体が重くなります（一般的な考え方）。

一方、インデックスは付けるほどよいわけではありません。行を追加・更新・削除するたびに、インデックスも書き換える必要があるので、書き込みが遅くなり、容量も増えます。使われないインデックスは、弱点だけが残ります。

どの検索が遅いのかは、推測ではなく、実際に実行されているクエリとかかった時間を見て決めます。公式ドキュメントによると、クエリビルダーの `dumpRawSql()`・`ddRawSql()` で、値を埋め込んだ実際の SQL を表示できます。その SQL の前に `EXPLAIN` を付けて実行すると、インデックスが使われているか、すべての行を読んでいるかを確かめられます。`EXPLAIN` は PostgreSQL や MySQL など多くのデータベースにあり、SQLite では `EXPLAIN QUERY PLAN` と書きます（データベースの一般的な機能）。

## どこに書くか

| 付ける列 | 例 |
| --- | --- |
| `where` でよく絞り込む列 | `status`、`user_id` |
| `orderBy` でよく並べ替える列 | `created_at`、`published_at` |
| 絞り込みと並べ替えを一緒に使う | `index(['user_id', 'created_at'])` |
| 値が重複してはいけない列 | `unique('email')` |

どの列に付けるかの判断は、一般的な考え方です。複合インデックスは先頭の列から順に使われるので、「絞り込む列 → 並べ替える列」の順に並べます。

外部キーの列（`user_id` など）も、よく検索に使います。外部キーを付けたときに、その列に自動でインデックスが作られるかは、データベースによって違います。たとえば MySQL（InnoDB）は作りますが、PostgreSQL は作りません（データベースの一般的な知識）。自動で付くと決めつけず、検索に使う外部キーの列には、インデックスがあるかを確かめます。

公式ドキュメントによると、大きなテーブルにインデックスを作ると、作っている間テーブルがロックされ、読み書きが止まることがあります。本番のテーブルに追加するときは、時間帯や作り方に気をつけます。PostgreSQL と SQL Server では、インデックスの定義に `online()` をつなげると、テーブルをロックせずにインデックスを作れます。

## 良い例と悪い例

悪い例: 検索に使わない列まで、すべてにインデックスを付ける。

```php
$table->index('note');
$table->index('amount');
$table->index('status');
```

なぜ悪いか: 使われないインデックスは速さに役立たず、保存のたびに書き換えるぶん遅くなります。

良い例: 実際の検索の条件と並べ替えに合わせて付ける。

```php
// Order::where('user_id', $id)->latest()->paginate(20) に合わせる
$table->index(['user_id', 'created_at']);
```

## AIが書きがちな誤り

- 遅いと聞いて、検索に使わない列も含めて、あらゆる列にインデックスを付ける
- 複合インデックスの列の順番を、検索の条件と合わない順にする
- 外部キーの列には、いつも自動でインデックスが付くと考える
- インデックスの代わりに、PHP で全件を取り出して絞り込む

インデックスを見たら、「どの検索で使われるか」「保存の多いテーブルに、使われないインデックスはないか」を確かめましょう。

## まとめ

- インデックスは、値から行をすぐに引けるようにして、検索と並べ替えを速くする
- `where`・`orderBy` でよく使う列、外部キーの列に付ける
- 複合インデックスは、絞り込む列 → 並べ替える列の順にする
- 付けすぎると書き込みが遅くなる。大きなテーブルへの追加は、ロックに注意する
