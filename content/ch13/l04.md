## 概念

Laravel は、リクエストのたびに設定ファイルを読み、ルートを登録し、Blade をコンパイルします。本番では、これらを先にまとめてキャッシュしておくことで、起動を速くできます。

| コマンド | 公式ドキュメントの説明 |
| --- | --- |
| `config:cache` | 設定ファイルを1つのキャッシュのファイルにまとめる |
| `event:cache` | 自動で見つけたイベントとリスナーの対応をキャッシュする |
| `route:cache` | ルートの登録を、キャッシュのファイルの中の1回の呼び出しにまとめる |
| `view:cache` | すべての Blade のビューを先にコンパイルしておく |

公式ドキュメントによると、`php artisan optimize` は、これらのファイルをまとめてキャッシュするコマンドで、デプロイの手順の中で実行します。

```bash
php artisan optimize        # まとめてキャッシュを作る
php artisan optimize:clear  # optimize で作ったキャッシュを消す
```

設定のキャッシュで `.env` が読まれなくなること、`env()` を設定ファイルの中だけで使う理由は、第2章で扱いました。

## なぜ必要か

本番では、同じ設定やルートを、リクエストのたびに読み直す必要はありません。キャッシュしておけば、その分の処理を省けます。

一方、キャッシュは「作ったときの状態」を使い続けます。ルートをキャッシュした後に `routes/web.php` を変えても、キャッシュを作り直すまでは使われません（Laravel 本体の実装による動き）。開発中はルートや設定をよく変えるので、キャッシュがあると「変えたのに動きが変わらない」原因になります。公式ドキュメントも、設定のキャッシュは開発中に実行しないよう書いています。

## どこに書くか

| 場面 | すること |
| --- | --- |
| 本番のデプロイ | 新しいコードと依存パッケージを取り込んだ後に `php artisan optimize` |
| 開発中 | キャッシュを作らない。作ってしまったら `optimize:clear` |
| 本番で設定やルートを変えた | もう一度デプロイし、キャッシュを作り直す |

デプロイの手順では、順番が大切です。`git pull` の前に `optimize` を実行すると、古いコードのキャッシュができ、取り込んだ新しいルートやビューが使われません。新しいコードを取り込んでからキャッシュを作ります（一般的な考え方）。キャッシュはデプロイのたびに作り直すので、本番のサーバーで手で打つより、デプロイの手順（スクリプト）に書いておくと忘れません。本番の `APP_DEBUG` を `false` にすること（第12章）も、デプロイのときに確かめる項目です。

公式ドキュメントによると、`optimize:clear` は、`optimize` で作ったキャッシュのファイルに加えて、既定のキャッシュのストアのすべての値も消します。アプリが `Cache` で入れたデータ（前のレッスン）も消えるので、本番で気軽に実行するコマンドではありません。

## 良い例と悪い例

悪い例: 開発中に、速くするために `optimize` を実行する。

```bash
# 開発環境で
php artisan optimize
```

なぜ悪いか: ルート・ビュー・設定の変更が、キャッシュを消すまで反映されなくなります。

良い例: 本番のデプロイの最後のほうで実行する。

```bash
git pull origin main
composer install --no-dev
php artisan migrate --force
php artisan optimize
php artisan queue:restart
```

公式ドキュメントによると、キューのワーカーは長く動き続けるプロセスで、コードの変更に気づかないので、デプロイのときに `queue:restart` で再起動します。`queue:restart` はワーカーを終了させるだけなので、Supervisor などのプロセス管理の仕組みが起動し直します（第9章）。

## AIが書きがちな誤り

- 開発環境で、速くするために `php artisan optimize` や `route:cache` を勧める
- デプロイの手順で、新しいコードを取り込む前にキャッシュを作る
- 変更が反映されない原因を、キャッシュを確かめずにブラウザやコードのせいにする
- 本番で、`optimize:clear` がアプリのキャッシュまで消すことを知らずに実行する

キャッシュのコマンドを見たら、「今は本番のデプロイか、開発中か」「新しいコードを取り込んだ後か」を確かめましょう。

## まとめ

- `optimize` は、設定・イベント・ルート・ビューをまとめてキャッシュし、起動を速くする
- 本番のデプロイの手順で、新しいコードを取り込んだ後に実行する
- 開発中は使わない。キャッシュを作り直すまで変更が反映されない
- `optimize:clear` は、キャッシュのファイルと、既定のキャッシュのストアの値を消す
