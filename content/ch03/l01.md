## 概念

クラスが仕事をするために使う別のオブジェクトを、**依存**と呼びます。たとえば、注文を受け付けるコントローラーが決済サービスを使うなら、決済サービスはコントローラーの依存です。

依存を手に入れる方法は2つあります。

- **自分で作る**: クラスの中で `new PaymentGateway()` と書く
- **外から受け取る**: コンストラクタやメソッドの引数で受け取る。これを**依存性の注入**（Dependency Injection、DI）と呼ぶ

Laravel のコントローラー・ミドルウェア・イベントリスナーなどは、**サービスコンテナ**が作ります。コンテナは、コンストラクタに書かれた型を見て、必要なオブジェクトを作って渡します。

```php
class OrderController extends Controller
{
    public function __construct(
        private PaymentGateway $gateway,
    ) {}
}
```

このように型を書くだけで、`$this->gateway` に `PaymentGateway` が入ります。

## なぜ必要か

公式ドキュメントは、依存を注入する利点として、テストで依存を偽物（モック）に差し替えられることを挙げています。

決済サービスを使うコントローラーをテストするとき、本物の決済 API を毎回呼ぶわけにはいきません。依存を外から受け取るクラスなら、テストのときだけ偽物を渡せます。クラスの中で `new` していると、偽物を渡す入口がありません。

もう1つの利点は、組み立て方を1か所にまとめられることです。`new PdfRenderer(config('services.pdf.key'))` のように、依存を作るには設定の値やさらに別の依存が必要なことがあります。これを使う側でそれぞれ書くと、組み立て方が変わったときに、すべての箇所を直すことになります（これは公式ドキュメントの記載ではなく、一般的な考え方です）。

## どこに書くか

| 依存の種類 | 受け取り方 |
| --- | --- |
| コントローラー全体で使うサービス | コンストラクタの引数 |
| 1つのアクションだけで使うサービス | そのメソッドの引数 |
| `Request` やルートのモデル | メソッドの引数 |

`new` してよいのは、データを入れるだけの小さなオブジェクト（値オブジェクトや DTO など）です。外部と通信するもの、設定が必要なもの、テストで差し替えたくなるものは、注入で受け取ります（一般的な考え方）。

## 良い例と悪い例

悪い例: メソッドの中で依存を組み立てる。

```php
public function store(Request $request)
{
    $mailer = new ReportMailer(new PdfRenderer(config('services.pdf.key')));
    $mailer->send($request->user());

    return back();
}
```

なぜ悪いか: テストで本物のメール送信を止められません。PdfRenderer の作り方も、このコントローラーが知っていなければなりません。

良い例: 依存を引数で受け取る。

```php
public function store(Request $request, ReportMailer $mailer)
{
    $mailer->send($request->user());

    return back();
}
```

ReportMailer をどう組み立てるかは、コンテナに任せます。その方法は、この章の後のレッスンで扱います。

## AIが書きがちな誤り

- コントローラーのメソッドの中で、外部 API のクライアントやサービスを `new` する
- 依存の組み立て（設定の値の読み込みなど）を、使う側のコードに毎回書く
- 「テストしやすくするため」と言いながら、テストで差し替えられない書き方のまま残す

コードの中に `new` を見つけたら、「これはテストで差し替えたくなるものか」を確かめましょう。

## まとめ

- 依存性の注入は、使うオブジェクトを中で作らず、引数で外から受け取ること
- コントローラーなどはコンテナが作るので、型を書くだけで依存を受け取れる
- 注入しておけば、テストで依存を偽物に差し替えられる
- 組み立て方を使う側から追い出し、1か所にまとめられる
