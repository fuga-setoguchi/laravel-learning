## 概念

コンテナに「このクラスはこう作る」と教えることを**結合**（binding）と呼びます。結合には、作ったインスタンスをどれだけ使い回すかによって、主に3つの種類があります。

| 種類 | 取り出したときに返すもの |
| --- | --- |
| `bind` | 毎回、新しく作ったインスタンス |
| `singleton` | 最初に作ったインスタンス。その後も同じものを返し続ける |
| `scoped` | 1つのリクエストやジョブの間は同じインスタンス。次のリクエストやジョブでは作り直す |

```php
// AppServiceProvider の register メソッド
$this->app->bind(ReportBuilder::class, fn (Application $app) => new ReportBuilder(/* ... */));
$this->app->singleton(ExchangeRateClient::class, fn (Application $app) => new ExchangeRateClient(/* ... */));
$this->app->scoped(CurrentTenant::class, fn (Application $app) => new CurrentTenant());
```

公式ドキュメントは、結合のほとんどはサービスプロバイダに登録すると説明しています。第1章で扱ったとおり、`register` ではコンテナへの結合だけを行います。

## なぜ必要か

使い分けを誤ると、目に見えにくい不具合になります。

`singleton` は、一度作ったインスタンスを返し続けます。ふつうの Web のリクエストでは、リクエストが終わると全体が片付くので、問題が表に出にくいです。ところが、キューのワーカーや Octane のように、プロセスを終えずに次々と処理を続ける環境では、同じインスタンスが次のジョブやリクエストにも使われます。リクエストごとの状態を持つクラスを `singleton` にすると、前の人の状態が次の人に混ざります。

公式ドキュメントは、`scoped` のインスタンスは新しいリクエストやジョブが始まると捨てられると説明しています。リクエストやジョブの中だけで共有したいものには、`scoped` が向いています。

## どこに書くか

選び方は、公式ドキュメントの記載ではなく、一般的な考え方です。

| クラスの性質 | 選ぶもの |
| --- | --- |
| 状態を持たず、作るのに手間がかかる（API のクライアントなど） | `singleton` |
| 1つのリクエストやジョブの中で共有したい状態を持つ | `scoped` |
| 使うたびにまっさらな状態がほしい | `bind`（または結合しない） |

結合は `AppServiceProvider` などの `register` に書きます。単純な対応だけなら、プロバイダの `$bindings` と `$singletons` プロパティにまとめて書けます。

サービスプロバイダに書く代わりに、クラス（またはインターフェース）に属性を付ける方法もあります。`#[Singleton]` を付けると1回だけ、`#[Scoped]` を付けるとリクエストやジョブごとに1回だけ作られます。

```php
use Illuminate\Container\Attributes\Scoped;

#[Scoped]
class OrderSummary { /* ... */ }
```

```php
public $singletons = [
    ExchangeRateClient::class => ExchangeRateClient::class,
];
```

## 良い例と悪い例

悪い例: 状態を持つクラスを `singleton` にする。

```php
// OrderSummary は $lines に明細をためるクラス
$this->app->singleton(OrderSummary::class, fn () => new OrderSummary());
```

なぜ悪いか: キューのワーカーの中では、前のジョブで追加した明細が次のジョブにも残ります。

良い例: ジョブやリクエストごとに作り直す。

```php
$this->app->scoped(OrderSummary::class, fn () => new OrderSummary());
```

## AIが書きがちな誤り

- 「インスタンスを使い回すほうが速い」という理由で、何でも `singleton` にする。クラスに `#[Singleton]` 属性を付ける場合も同じで、状態を持つクラスには付けない
- ログイン中のユーザーやリクエストの値を、`singleton` のクラスのプロパティに保存する
- 結合を `boot` に書く（第1章で扱ったとおり、結合は `register`）

`singleton` を見つけたら、「このクラスはプロパティに状態をためていないか」を確かめましょう。

## まとめ

- `bind` は毎回新しく、`singleton` はずっと同じ、`scoped` はリクエストやジョブごとに同じインスタンスを返す
- 状態を持つクラスを `singleton` にすると、長く動くプロセスで状態が持ち越される
- 状態を持たない、作るのに手間がかかるものは `singleton` に向く（一般的な考え方）
- 結合はサービスプロバイダの `register` に書く。単純な対応は `$bindings`・`$singletons` でもよい
