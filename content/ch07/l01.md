## 概念

**リレーション**は、テーブルどうしのつながりを、モデルのメソッドとして書いたものです。よく使うのは次の3つです。

| 関係 | 例 | 書き方 | 外部キー |
| --- | --- | --- | --- |
| 1対多 | ユーザーと記事 | User に `hasMany(Post::class)` | 「多」の側の posts に `user_id` |
| 1対多の逆 | 記事から見たユーザー | Post に `belongsTo(User::class)` | 自分の posts の `user_id` |
| 多対多 | 記事とタグ | 両方に `belongsToMany(...)` | 中間テーブル post_tag に `post_id` と `tag_id` |

```php
class User extends Model
{
    public function posts(): HasMany
    {
        return $this->hasMany(Post::class);
    }
}

class Post extends Model
{
    public function user(): BelongsTo
    {
        return $this->belongsTo(User::class);
    }

    public function tags(): BelongsToMany
    {
        return $this->belongsToMany(Tag::class);
    }
}
```

公式ドキュメントによると、外部キーの列の名前は、規約で決まります。`hasMany` では親のモデル名のスネークケースに `_id` を付けた名前（`user_id`）、多対多の中間テーブルは2つのモデル名をアルファベット順に並べた名前（`post_tag`）です。

## なぜ必要か

外部キーの置き場所は、関係の形で決まります。「1」の側に「多」の id を置こうとすると、1行に1つしか入らないので表せません。多対多では、どちらの側にも置けないので、中間テーブルを作ります。AIが関係の形を取り違えると、あとで「タグを2つ付けたい」となったときに、テーブルを作り直すことになります。

リレーションをメソッドとして書いておくと、`$post->user` や `$user->posts()->where(...)` のように、外部キーを意識せずに関連するデータを扱えます。

## どこに書くか

| やりたいこと | 書き方 |
| --- | --- |
| 関連するデータをまとめて使う | `$user->posts`（プロパティ。結果のコレクション） |
| 条件を足して問い合わせる | `$user->posts()->where(...)`（メソッド。問い合わせのビルダー） |
| 外部キーの列と制約を作る | マイグレーションで `$table->foreignId('user_id')->constrained()` |
| 多対多のつながりを入れ替える | `$post->tags()->sync([1, 2, 3])` |

`$user->posts` は、そのユーザーの記事をすべて読み込みます。件数を数えたり絞り込んだりするなら、`$user->posts()` に条件を足して、データベースに任せます。

外部キーの列は、`foreignId()->constrained()` で外部キー制約を付けて作ります。存在しない id が入るのを、データベースが防ぎます（制約を付ける理由は一般的な考え方）。

公式ドキュメントによると、`attach` や `sync` などの中間テーブルの操作には、`attachOrFail` や `syncOrFail` のように、操作をトランザクションで包む版もあります。途中で例外が起きると、変更はすべてロールバックされます。トランザクションは、この章の3つ目のレッスンで扱います。

## 良い例と悪い例

悪い例: 多対多の関係を、posts の列1つで表す。

```php
// posts テーブルに tag_id を足し、Post に belongsTo(Tag::class) を書く
```

なぜ悪いか: 記事1つにタグ1つしか付けられません。

良い例: 中間テーブルを作り、`belongsToMany` で結ぶ。

```php
Schema::create('post_tag', function (Blueprint $table) {
    $table->foreignId('post_id')->constrained()->cascadeOnDelete();
    $table->foreignId('tag_id')->constrained()->cascadeOnDelete();
    $table->primary(['post_id', 'tag_id']);
});
```

`primary(['post_id', 'tag_id'])` で、記事とタグの組み合わせを一意にしています。同じ記事に同じタグが2回付くのを、データベースが防ぎます（組み合わせを一意にするのは一般的な考え方）。

## AIが書きがちな誤り

- 多対多の関係を、列1つやカンマ区切りの文字列で表す
- `$user->posts->where(...)->count()` のように、すべて読み込んでから PHP で絞り込む
- 外部キーの列を `unsignedBigInteger` だけで作り、制約を付けない
- フォームで選ばれたタグに入れ替えるのに、`attach` を使って古いタグを残す

リレーションを見たら、「外部キーはどちらのテーブルにあるか」「関係の形（1対多か多対多か）は仕様に合っているか」を確かめましょう。

## まとめ

- 1対多は「多」の側に外部キーを置き、`hasMany` と `belongsTo` で結ぶ
- 多対多は中間テーブルを作り、`belongsToMany` で結ぶ
- `$user->posts` は結果、`$user->posts()` は問い合わせ。絞り込みや数えるのはメソッドで
- 外部キーの列には `constrained()` で制約を付ける
