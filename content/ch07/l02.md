## 概念

リレーションのプロパティ（`$book->author`）は、初めて使うときにデータベースから読み込まれます。公式ドキュメントは、これを遅延読み込み（lazy loading）と呼んでいます。

一覧の中でリレーションを使うと、この遅延読み込みが1件ごとに走ります。

```php
$books = Book::all();               // 1回

foreach ($books as $book) {
    echo $book->author->name;       // 1冊ごとに1回
}
```

25冊なら、本を取り出す1回と、著者を取り出す25回で、26回の問い合わせになります。これを **N+1 問題**と呼びます。

防ぐには、一覧を取り出すときに、使うリレーションを `with` で先に読み込みます。これを **Eager Loading** と呼びます。

```php
$books = Book::with('author')->get();   // 本で1回、著者で1回の合わせて2回
```

## なぜ必要か

N+1 問題は、データが少ない開発中には気づきにくく、件数が増えた本番で遅くなります。コードは正しく動くので、テストでも見つかりません。

AIが書くコードでは、コントローラーで一覧を取り出し、ビューでリレーションを読む形がよく出てきます。コントローラーとビューが別のファイルなので、読み込み忘れに気づきにくい組み合わせです。

## どこに書くか

| やりたいこと | 書き方 |
| --- | --- |
| 一覧を取り出すときに読み込む | `Book::with('author')->get()` |
| 複数のリレーション | `with(['author', 'publisher'])` |
| リレーションの先のリレーション | `with('author.contacts')` |
| 取り出した後のコレクションに読み込む | `$books->load('author')` |
| 一覧の各行で、関連するモデルの件数を使う | `Post::withCount('comments')` → `$post->comments_count` |
| 開発中に読み込み忘れに気づく | `Model::preventLazyLoading(! $this->app->isProduction())` |

読み込むリレーションに条件を付けたいときは、`with` にクロージャを渡します。公式ドキュメントの例と同じく、引数に型は書いていません。

```php
$users = User::with(['posts' => function ($query) {
    $query->where('status', 'published');
}])->get();
```

このクロージャに渡されるのは、リレーションのオブジェクト（`HasMany` など）です。Laravel 本体のコードでは、リレーションは `Illuminate\Contracts\Database\Eloquent\Builder` というインターフェースを実装していますが、`Illuminate\Database\Eloquent\Builder` クラスではありません。型を書くなら、インターフェースのほうを `use` します。

一覧で「記事ごとのコメント数」を表示するときに、ループの中で `$post->comments()->count()` を呼ぶと、1件ごとに問い合わせが走ります。公式ドキュメントによると、`withCount('comments')` を使えば、コメントを読み込まずに件数を取り出し、各モデルの `comments_count` で読めます。1人のユーザーの記事を数えるだけなら `$user->posts()->count()`、一覧の各行で数を使うなら `withCount`、と使い分けます。

子から親をたどるときも N+1 問題は起きます。公式ドキュメントによると、`Post::with('comments')` で記事からコメントを読み込んでも、ループの中で `$comment->post` を読むと、コメントごとに記事を取り出す問い合わせが走ります。リレーションの定義に `->chaperone()` を付けるか、`with` の中で `chaperone()` を呼ぶと、子に親が自動でセットされます。

```php
$posts = Post::with([
    'comments' => fn ($comments) => $comments->chaperone(),
])->get();
```

`preventLazyLoading` は、`AppServiceProvider` の `boot` で呼びます。公式ドキュメントのとおり、本番以外では、遅延読み込みが起きると例外になります。本番では例外にせず、画面が止まらないようにします。本番で遅延読み込みを記録だけしたいときは、`Model::handleLazyLoadingViolationUsing()` で、例外の代わりにログに書く処理を登録できます。

13.x には、読み込んでいないリレーションを自動でまとめて読み込む `Model::automaticallyEagerLoadRelationships()` もあります。ただし、何が読み込まれるかがコードに見えなくなるので、まずは `with` で明示する書き方を身に付けましょう（一般的な考え方）。

## 良い例と悪い例

悪い例: 一覧を取り出すときに読み込まず、ビューでリレーションを読む。

```php
$posts = Post::latest()->take(20)->get();
// ビューで $post->user->name を読む
```

なぜ悪いか: 記事1件ごとにユーザーを取り出す問い合わせが走ります。

良い例: ビューで使うリレーションを、コントローラーで先に読み込む。

```php
$posts = Post::with('user')->latest()->take(20)->get();
```

## AIが書きがちな誤り

- 一覧のビューでリレーションを読むのに、コントローラーで `with` を付けない
- N+1 問題を直すつもりで、ループの中で1件ずつ `load` する
- 親から子を `with` で読み込んだのに、ループの中で子から親（`$comment->post`）を読み、N+1 問題を残す
- 一覧の各行で `$post->comments()->count()` を呼び、`withCount` を使わない
- Eager Loading の条件のクロージャに、`Illuminate\Database\Eloquent\Builder` クラスを型宣言する（渡されるのはリレーションなので、型が合わずにエラーになる）
- `preventLazyLoading()` を引数なしで呼び、本番でも例外にしてしまう

一覧を表示するコードを見たら、「ビューで使っているリレーションを、`with` で読み込んでいるか」を確かめましょう。

## まとめ

- リレーションのプロパティは、初めて使うときに読み込まれる。一覧で使うと N+1 問題になる
- 一覧を取り出すときに `with` で先に読み込む
- 取り出した後なら、コレクションに一度だけ `load`
- 開発中は `preventLazyLoading` で読み込み忘れを例外にして気づく
